# ADR-0062 — The daemon exits once nothing refers to it, and a reference is a held socket

- Status: Accepted; implemented in `daemon` (`DaemonIdleWatchdog`, the `presence` command) with Studio, MCP, and the CLI's blocking waits holding references. Verify with `cd studio && ./gradlew :daemon:test`, then open and quit Studio with `WAILO_IDLE_LINGER_MINUTES=1` and watch the process go.
- Context: ADR-0058 made the daemon outlive its launcher and every client, with `wailo-cli stop` as the only shutdown path. That is correct while something is using it and indefensible when nothing is: the observed case was a daemon still resident after two days and ~49 MB, started by a Studio session long since closed. It is a background process the user never knowingly started, cannot see, and has no reason to keep. The property it was protecting — reopen Studio and yesterday's traffic is still listed — was never a guarantee anyway: it dies on reboot, on `wailo-cli stop`, and on the protocol-version replace ADR-0058 itself describes as accepting "the loss of that daemon's in-memory session".
- Decision:
  - **A reference is a held socket, and the daemon exits when it has none.** Frontends with a real lifetime open one extra connection carrying the `presence` command; the daemon answers it, then reads it only to learn when it dies.
  - **A device earns the daemon its life by capturing, not by being connected.** Traffic and breakpoint holds extend the idle window exactly as a CLI command does. A connected app is deliberately *not* a reference: a phone left plugged in with a debug build running would otherwise pin the daemon for as long as the cable is in, which is the state this decision exists to end. The device SDK is a live tap (ADR-0025), so a silent app loses nothing that a reconnect does not restore.
  - **Liveness is the kernel's, not a message's.** An `attach`/`detach` pair would leak its count forever the first time a frontend was force-quit or SIGKILLed, producing a daemon that never exits again — the same bug, in a form that is much harder to notice. The OS closes a socket on any death, so the count cannot drift. Presence readers park on virtual threads, which the control channel already uses.
  - **One-shot CLI invocations hold nothing, and a linger window covers them.** `wailo-cli status` lives about a second; if it held a reference it would start a daemon and take it down again on the way out, once per command. Instead every request pushes out an idle deadline (`idleLingerMinutes`, default 30, `0` disables it, `WAILO_IDLE_LINGER_MINUTES` overrides for tests). The window is measured from whichever came last — a request, captured traffic, or the last reference being released — so quitting Studio after hours of polling still buys a full window rather than an instant exit. `wait_exchange` and `wait_hold` are the exception: they block by design, so they do hold one.
  - **`serve --keep` is the explicit hold.** It blocks until Ctrl-C holding a presence connection, which pins the daemon through a CI run's gaps and makes its lifetime visible in a terminal instead of invisible in a process list. Plain `serve` still ensures-and-returns, because a script that expects it to return would otherwise hang forever.
  - **An idle exit is not an explicit stop.** It does not write `daemon.stopped`, so the next frontend starts a daemon normally; only `wailo-cli stop` suppresses relaunch. The control protocol version is bumped so a frontend that expects `presence` replaces an older daemon that would refuse it.
- Alternatives considered:
  - **Leave it running (ADR-0058 as written):** rejected — the cost is small but the surprise is not, and the state being protected is already not durable across the events that routinely end the process.
  - **An idle timer with no reference count:** rejected — the timeout has to be short to be useful and long to be safe, and it cannot tell "nobody is here" from "somebody is reading". Every value is wrong for one of the two.
  - **`attach`/`detach` RPCs, or a lease renewed by the poll loop:** rejected — the first leaks on a crash; the second is a clock to tune, and the poll interval is already an implicit heartbeat, so it would add a protocol for precision the held socket gives exactly and for free.
  - **A `launchd` LaunchAgent with socket activation:** rejected — the right mechanism at the OS level, but it needs an install step and makes Wailo a login item, which ADR-0058 explicitly declined.
  - **Persist captured traffic so an exit costs nothing:** rejected here, not on the merits — it is the only thing that would survive an actual exit, but writing captured bodies and credentials to disk is a different security posture in a project that redacts by default for MCP (ADR-0059), and it deserves its own decision rather than riding in on a lifecycle change.
- Consequences:
  - Traffic captured with no frontend open and nothing capturing since can now be lost to an exit that would previously not have happened. Configuration is unaffected: everything ADR-0061 made durable still reloads.
  - A Cursor or Claude session with the Wailo MCP configured pins the daemon for as long as that client lives. That is a correct reading of "something refers to it", but it means the daemon can be alive with no window anywhere on screen.
  - An attached device is dropped when the daemon goes, along with its `adb reverse` route and usbmux tunnel, even though the app never disconnected. Both ends re-establish on the next attach (ADR-0018/0046), so the cost is a reconnect rather than a relaunch.
  - Capture activity is sampled on the watchdog's own schedule rather than observed as it lands, so the recorded moment can trail the traffic by up to one check interval — at most 30s against a window measured in minutes.
  - Frontends already tolerate the restart: `DaemonLauncher.ensureRunning` starts one on launch and the poll loop relaunches on a failed poll, so losing a race against an exiting daemon self-heals within a reconnect interval.
