# ADR-0083 — The machine seam is required, so a test can never drive `networksetup`

- Status: Accepted. The remedy is a boundary rather than a patch, and the same shape can recur anywhere a class reconfigures the machine it runs on.
- Context: `SystemProxyController` rewrites this Mac's network settings through `networksetup`, and it already carries the seam that keeps that out of a test — `networksetup: NetworkSetup? = systemNetworkSetup()`, whose own KDoc says it is "the seam the tests use: this class reconfigures the machine it runs on, so exercising its decisions for real would be the very accident it exists to clean up". `SystemProxyTakeoverTest` passes a fake through it. `SystemProxyControllerTest` does not: `applyingOnAMachineWithoutNetworksetupChangesNothingAndSaysWhy` builds `SystemProxyController(statePath)`, taking the default, and calls `apply(9090)`. On macOS `supported` is true, so that is a real `-setwebproxy` / `-setsecurewebproxy` plus `state on` against every active network service — and every assertion in the test sits inside `if (!applied.supported)`, so on the one platform where it does damage it asserts nothing and passes green. The class KDoc claims the opposite of what the class does.
  - The damage is not "a setting changed". `apply` writes its undo record to the injected `statePath`, which here is a temp directory the test deletes in `@AfterTest`, so the real `~/.wailo/system-proxy.json` is never written. The takeover survives the suite; the recovery does not. That is the one combination ADR-0075 has no answer for, because its whole premise is that the record predates the change and outlives the process — `recover()` has nothing to replay, and `releaseStranded()` is the only cleanup left.
  - `releaseStranded()` then closes the trap rather than opening it. It stands down whenever the port answers ("a live listener means the takeover is working, and may belong to another daemon"), which is the right rule for two daemons and the wrong one here. So: the suite runs, the machine points at `127.0.0.1:9090`; with no Wailo proxy listening the machine has no internet at all, because everything that honours system proxy settings dials a dead port; the user starts the proxy to get back online, and that live listener is precisely what disarms the sweep that would have released the setting. The state is self-perpetuating, and the only exit is to start the proxy and then stop it, since `ProxyController.stop()` restores *and then* sweeps against a port that is by then dead.
  - Observed on a developer machine after a run of `:daemon:test`: `networksetup -getwebproxy Wi-Fi` reporting enabled at `127.0.0.1:9090`, no `~/.wailo/system-proxy.json`, and a user who had never turned the takeover on. Reported as "the internet suddenly drops and I have to turn the proxy on to get it back".
  - `WAILO_HOME` cannot contain this and was never meant to: `networksetup` changes the one Mac, and ADR-0078 deliberately pins the record to the real `~/.wailo` so that whichever daemon runs next can put the machine back. Isolation is available for the daemon's files and for the capture and proxy ports; there is none for the machine, which is exactly why the seam has to be the thing that protects it.
- Decision:
  - **The machine seam is required, not defaulted.** Drop the default from `networksetup` so constructing a `SystemProxyController` is a decision. The three production sites (`Main`, `DaemonServer`, `ProxyController`) pass `systemNetworkSetup()`; a test cannot reach the real machine by omission, which is how this one did. A default that is safe in production and catastrophic in a test is a default that belongs to neither.
  - **The record path and the machine travel together.** Redirecting `statePath` while keeping the real `networksetup` is what turned a recoverable takeover into a permanent one, so they stop being two independent arguments. A caller that fakes the machine gets the fake record path with it.
  - **A test that asserts nothing on the platform it runs on is not a test.** `applyingOnAMachineWithoutNetworksetupChangesNothingAndSaysWhy` is about the unsupported path, which is what the null seam exists to describe — so it passes `networksetup = null` explicitly and keeps its assertions on every platform, instead of guarding them behind the condition that makes them meaningful.
  - **A daemon that owns the listener but not the takeover treats the pointing as stranded.** `releaseStranded` infers "the takeover is live" from "the port answers", which cannot distinguish another daemon's takeover from this daemon's own listener sitting under a setting nobody in this process applied. `snapshot == null` while this process owns that port is unambiguous: we did not take the machine over, and the thing answering is us. It rides as an explicit `listenerIsOurs`, passed only by `ProxyController.start` once the listener is bound, so the inference stays off by default everywhere else.
- Alternatives considered:
  - **Skip the test on macOS:** rejected. It removes the symptom and leaves the loaded default in place for whatever is written next, which is the actual defect. It also deletes coverage on the only platform where the class does anything.
  - **Have the test restore in `@AfterTest`:** rejected, and instructively so. It cannot restore what it never wrote anywhere durable, and a suite killed part-way skips teardown entirely — which is the precise failure ADR-0075 exists to survive. A test cannot be the recovery mechanism for a design whose premise is that recovery must outlive the process.
  - **Point the test's `statePath` at the real `~/.wailo/system-proxy.json`:** rejected. It would make the takeover recoverable by the next daemon, which is strictly better than today, but it is still a test writing the developer's machine state and still drops the network for the length of the run and beyond.
  - **Let `apply()` detect a test classpath and refuse:** rejected. Production code that behaves differently under test is code whose tested behaviour is not the shipped one, and the seam it already has is the correct mechanism.
- Consequences:
  - `cd studio && ./gradlew :daemon:test` stops reconfiguring the machine that runs it. That is the whole point, and it is checkable: `networksetup -getwebproxy Wi-Fi` must read identically before and after, and `~/.wailo/system-proxy.json` must not appear.
  - Three production construction sites gain an explicit argument. Nothing else changes for a shipped build — the takeover is still session state, still snapshot-before-write, still recovered by the next daemon.
  - Anyone whose machine is stranded today gets out with `wailo-cli set_proxy --on` followed by `--off` (or the same pair in Studio), because `stop()` restores, drops the listener, and only then sweeps — by which point the port is dead and the sweep can act. Turning it off in System Settings works too, and is the only option when no daemon will start.
  - The AGENTS.md note that `WAILO_HOME` does not isolate `set_system_proxy` should say the same of the test suite, since a contributor reading it today would reasonably conclude that a scratch state directory made the suite safe to run.
  - Manual smoke (two-tier verification): with the machine on a direct connection, run `:daemon:test`, then check the Network pane's Proxies tab — unchanged. Then take the takeover for real from Studio, `pkill -9` the daemon, and confirm the machine has no network; start any frontend and confirm the next daemon puts it back from the record. Finally, with no record on disk and the proxy running under a pointing nobody applied, confirm the daemon releases it rather than leaving the loop above.
