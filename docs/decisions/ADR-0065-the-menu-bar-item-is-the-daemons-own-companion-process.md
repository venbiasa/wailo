# ADR-0065 — The menu bar item is the daemon's own companion process, not Studio's window

- Status: Accepted; implemented as the `menubar` module (`Main.kt`, `TrayMenu`, `TrayIcon`, `StudioLauncher`), spawned by `DaemonLauncher.ensureMenubar()`, with `request_show_studio` / `request_quit` and a presence *kind* added to the daemon's control protocol (version 4). Verify by hand: run `wailo-cli status`, confirm an item appears with no Studio open, use Show Studio from it, quit Studio alone and confirm the item stays, then Quit from the item and confirm no `com.venbiasa.wailo.daemon.MainKt` process survives.
- Context: ADR-0063 gave the item to Studio, which meant it existed only when Studio did. That is backwards for what the item is *for*: the case where nobody can tell Wailo is running is precisely the case with no window — an MCP session in an editor, or a CLI command that started a daemon and left. It also forced two distortions to make the story hold: Studio had to keep referring to the daemon while hidden (reversing ADR-0062 for one frontend), and Studio's Quit had to stop the daemon, because otherwise closing the visible app left an invisible process with nothing on screen to attribute it to. Neither was true to the model where the daemon is the owner and every UI is a client of it (ADR-0058).
- Decision:
  - **The item is drawn by a small companion process, one per state directory.** `menubar` is a plain AWT `SystemTray` agent — no Compose — spawned by the same `DaemonLauncher` call every frontend already makes to get a daemon, so the icon appears for Studio, the CLI, and MCP alike. It holds an OS file lock for its lifetime; that lock *is* the single-instance protocol and is also how anything else asks whether an item exists.
  - **The daemon stays headless.** The agent is a separate process and a client of the same loopback API, so no UI toolkit or event loop enters `engine`, `host`, or `daemon`. The invariant is unchanged; only the count of frontends went up by one.
  - **The agent is not a reference (ADR-0062 preserved).** It never holds a presence socket. A process whose job is to report the daemon's lifetime must not extend it, or the icon would keep alive exactly the daemon it claims to be merely observing. Instead the agent watches the control channel and exits once the daemon has been gone for a few seconds — a grace window, so a daemon being *replaced* on a protocol bump does not take the icon down with it.
  - **The daemon relays the two asks the agent cannot make directly.** Show Studio and Quit need to reach a window in another process that the agent did not start. Both go through the daemon as monotonic counters in the poll every frontend already runs (`request_show_studio`, `request_quit`); a frontend acts on an *increase*, ignoring the value it found on connect, so nothing replays at launch and nothing is lost between polls. Presence now also carries a client *kind*, which is what lets Show Studio raise the Studio that is attached instead of starting a second one.
  - **Quit belongs to the item; Cmd-Q belongs to Studio.** Quit asks every frontend to exit, then stops the daemon explicitly — suppressing relaunch, so an attached MCP session's next call fails rather than quietly starting a fresh, empty daemon. Studio's own Cmd-Q now only ends Studio: the item survives to say the daemon is still there, and ADR-0062's idle exit takes it from there.
  - **Closing Studio's window hides it only when an agent is up.** The check is the agent's lock, asked at close time rather than at launch, because the agent is spawned alongside the window and may not have claimed it yet. With no item to restore from, close still quits.
- Alternatives considered:
  - **Keep it in Studio (ADR-0063):** rejected on the evidence of its own consequence list — it cannot show an item for a headless session, which is the whole motivating case.
  - **Tray code inside the daemon process:** rejected — breaks the headless invariant, and a daemon that owns an AWT event loop can no longer be the thing that runs anywhere.
  - **A Compose Desktop agent, reusing Studio's tray code:** rejected — this process is resident for as long as any daemon is, and a Compose runtime kept alive to draw five rows would cost more than the daemon it advertises.
  - **Let the agent hold a presence reference:** rejected — the daemon could then never idle out while an icon was on screen, which is ADR-0062 undone by its own status indicator.
  - **Have the agent spawn Studio for every Show Studio:** rejected — a second Studio beside the first is worse than the buried window it was meant to raise. Launching is the fallback for when the poll says none is attached.
  - **Signal Studio directly (a socket the agent owns, or an OS event):** rejected — the agent did not start Studio and cannot address it, whereas the daemon already talks to every frontend on a channel that is authenticated and polled.
- Consequences:
  - Any command that starts a daemon now also puts an icon on the user's screen — the intended effect, and the reason `WAILO_NO_MENUBAR` exists for CI and scripted runs. A machine with no system tray records that once, so it costs one JVM ever rather than one per command.
  - Studio's Quit is no longer destructive, and the "stop everything" affordance lives in exactly one place. Users who expect Cmd-Q to end Wailo entirely will find the daemon still up — reported honestly by the item, which is the point.
  - The agent inherits the classpath of whichever frontend spawned it, so Show Studio can only *launch* Studio when Studio was on that classpath. Started from an MCP session, the row disables itself rather than failing on click.
  - The control protocol went to version 4. Bumping it exposed that the replacement path assumed it was the only frontend on the machine: an updated Studio stopped the outdated daemon, a long-lived older frontend (an editor's MCP adapter) immediately started its own, and the updated one gave up with a hard error. `DaemonLauncher` now marks the explicit-stop flag itself for the length of the handover — which suppresses every other frontend's auto-restart, rather than trusting the build being replaced to do it — and retries the replacement until its deadline instead of failing on the first old daemon it sees. So an update is a handover, not a race, and the surviving failure mode names the cause.
  - macOS wants a monochrome template glyph while other trays take a colored icon, so the agent derives a silhouette from the Wailo mark and hands it over as a *template* (`apple.awt.enableTemplateImages`), letting the system tint it. Picking the colour here instead — from `AppleInterfaceStyle`, which was the first implementation — is not a shortcut but a wrong answer: the menu bar goes dark over a dark wallpaper while the OS is still in light mode, so the glyph came out black on black for the users most likely to have one. No preference key reports that state; only the system knows, so only the system can colour it.
  - The agent has no window, so a running agent and one whose icon the desktop silently dropped looked identical, and its log stayed empty on every success path. It now records that it is drawing the item, and names the state directory it failed to find a daemon in — the one question an agent cannot be asked, since a stray `WAILO_HOME` points it at a different daemon entirely.
