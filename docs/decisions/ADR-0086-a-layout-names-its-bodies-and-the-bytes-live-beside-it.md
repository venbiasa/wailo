# ADR-0086 — A rule layout names its bodies; the bytes live beside it, one file per rule

- Status: Accepted. Map Local and seed rules carry `bodySize` + `bodyHash` instead of `bodyBase64`; the bytes are files under `rule-bodies/<family>/<digest of id>`, resident in the daemon, fetched by frontends through `read_rule_body`. Control protocol 14. `cd studio && ./gradlew :daemon:test :desktopApp:test :host:test :mcp:test :shared:jvmTest` is green.
- Context: ADR-0085 put a rule's bytes on the rule, which was right about *ownership* and wrong about *shape*. A body is the largest thing in the system a user authors by hand — a captured response saved as a fixture is routinely megabytes — and once it rode inline it was inside three things that have nothing to do with it:
  - `map-local.json`, so a fixture set of a few megabytes was rewritten in full every time any rule was reordered, renamed or switched off. The write is synchronous with the publish.
  - every `replace_map_local` / `replace_seeds` request, so the same megabytes were base64-encoded, sent over loopback and decoded on the other side for a one-bit change.
  - every poll response whose layout hash had moved, so each attached frontend was handed the whole fixture set again, and Studio kept a second copy of all of it on the heap for rules it was not looking at.

  A toggle is a click. Paying a multi-megabyte encode, write and broadcast for one is not a tuning problem; it is the wrong unit. ADR-0069 had already answered this question for captured traffic — a retained exchange holds body *references* and the bytes are spooled — and authored rules were the one place bytes still travelled with their metadata.

  ADR-0085 explicitly rejected "keep the body files and publish a reference instead of the bytes". That rejection stands and this is not it. The thing it refused was a body file *in Studio* that the daemon would have to be told about, which is the mirror it deleted. Here the daemon owns both halves: it holds the bytes and it writes the reference. There is no second original and no way for the two to disagree, because only one process writes either.
- Decision:
  - **The layout names a body; it never contains one.** A rule DTO carries `bodySize` and `bodyHash` (SHA-256, empty for an empty body). The bytes live in `DaemonRuleBodyStore`, one file per rule, keyed by family.
  - **The daemon derives the reference; a frontend only repeats it.** A publish carries a `bodies` map of just the rules whose bytes changed. For everything else the daemon keeps what it already holds and recomputes size and digest itself, so a frontend can never name a body the daemon does not have.
  - **Bodies are resident in the daemon, not read per match.** A Map Local rule answers on the device and relay paths synchronously; a body that had to be loaded there could fail to arrive, which is exactly the "this rule's body did not load" state ADR-0085 retired with `bodyAvailable`. A file is where a body *persists*, never where it is looked up.
  - **A frontend fetches a body only when it is about to show or send it**, through `read_rule_body`. Studio reads one when a rule is opened in the editor or exported; MCP reads one for `get_map_local` / `get_seed` and for nothing else. `list_map_local` still reports `body_bytes` from the reference, so the cheap answer stays cheap.
  - **That read is not capped, unlike `read_body`.** The cap there keeps a caller from pulling a spooled multi-gigabyte capture into the daemon's heap, and a preview truncated at 8 MB is the answer a body viewer wants. Neither applies here: a rule body is resident before anyone asks for it, so the range is already bounded by the body, and both callers that want the whole thing — the editor and the exporter — save back what they are handed. A silent short read there is data loss. The offset/length range stays for MCP, which asks for a preview and says so with `output_truncated`.
  - **The digest is the frontend's receipt.** Studio stages authored bytes in `pendingBodies` and drops an entry only when the daemon reports that rule's `bodyHash` equal to the digest of the staged copy. Clearing on "we sent it" instead re-published stale bytes when a second edit landed inside the round trip.
  - **A publish sweeps the family it publishes.** Any body no rule in the new layout claims is deleted, on every publish and at startup — so a rule removed through the CLI, and one written by a daemon that died mid-edit, both get collected.
  - **The id is digested into the file name, never spelled out.** Ids arrive from MCP and CLI callers, so a literal name would let one containing `../` address a path outside the state directory, and two differing only in case would share a file on a case-insensitive volume.
  - **The capture filter is hash-gated too.** It was the last payload re-encoded and re-sent on every poll tick regardless of change; it now follows the rule families' pattern and arrives only when its hash moves.
- Alternatives considered:
  - **Reuse `BodyStore` / `SpoolBodyStore`, the daemon's existing encrypted body spool:** rejected because it is built for the opposite lifetime. It is capture-session state — cleared with the traffic, bounded by a retention cap, and designed to be thrown away — and an authored fixture must survive exactly what that store is built to discard.
  - **Keep bodies inline and gate the publish on a dirty flag** so an unchanged rule's bytes are omitted: rejected because it is the same reference idea with the reference left implicit. The receiver could not verify what it kept, and the persistence half — rewriting the whole file on every publish — is untouched.
  - **One sidecar file per rule holding both metadata and body:** removes the big rewrite too, but makes the layout — the order, the grouping — something to be reassembled from a directory listing rather than read. ADR-0081 made the layout a first-class thing the daemon owns; splitting it across N files to save a body is the wrong trade.
  - **Stream bodies over a separate channel instead of base64 in JSON:** worth doing if a single body ever becomes the bottleneck, but the cost here was sending bodies *at all* on unrelated edits, and that is gone. Base64 on the one body a user actually opened is not worth a second transport.
- Consequences:
  - A layout publish is now proportional to the number of rules, not the size of their bodies: a toggle or a reorder is a few hundred bytes and a small file write, whatever the fixture set weighs.
  - Studio's heap no longer holds a copy of every fixture body. `DaemonClient`'s rules carry the reference; the bytes exist only for the rule in the editor and for the duration of an export.
  - The control protocol goes to 14. `bodyBase64` survives on the DTO as a read-only migration field: a `map-local.json` or `seeds.json` written inline is adopted into the body store on first load and rewritten without it, once, so an existing install pays the cost one final time.
  - `HostMapLocalRule` / `HostSeed` gained `bodySize` and `bodyHash` constructor parameters, because a client-side rule built from a DTO has no bytes to derive them from and panels display the size. On the daemon they are still derived from the body it holds.
  - `DaemonClient.replaceMapLocalNodes` / `replaceSeedNodes` fold any bytes a caller left on the rules themselves into the `bodies` map. Studio publishes rules it read back from the daemon and so contributes nothing there, but a headless caller that built rules in memory would otherwise have its bodies silently dropped.
  - `RuleArchiveIo.buildArchive` is `suspend` and runs off the UI thread: an export now fetches each body rather than finding it already in hand.
  - Manual smoke (two-tier verification): with a large fixture set loaded, toggle a rule and confirm the panel responds immediately and `map-local.json`'s modified time changes without its size moving. Open the rule — the body is there. Edit the body, quit, reopen — the edit survived. Delete a rule and confirm its file under `rule-bodies/` is gone. Export, delete, import — bodies come back. Read the same fixture through MCP `get_map_local` and confirm the body and its truncation flag match the editor.
