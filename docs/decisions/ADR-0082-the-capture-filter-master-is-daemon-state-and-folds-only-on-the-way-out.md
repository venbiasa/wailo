# ADR-0082 — The capture filter's master is daemon state, and the fold happens only on the way to devices

- Status: Accepted; the master lives on `HeadlessHost` beside the Map Local, breakpoint, and seed masters, rides the wire as `captureFilterEnabled` at protocol version 11, and `set_capture_filter_enabled` exists in the CLI and MCP. `cd studio && ./gradlew :daemon:test :cli:test :mcp:test` is green, including a restart case in `DaemonIntegrationTest` and a fold case in `WailoMcpServiceTest`.
- Context: The capture filter was the last feature master that was not daemon state. Studio folded it into the two per-list flags before pushing — `allowlistEnabled = master && allowEnabled` — and the daemon stored the folded result, because the only thing it stored was the device-facing `CaptureFilter` protobuf, which has no room for a master. That encoding is lossy in the one place it matters: `blocklistEnabled: false` beside a non-empty `blockPatterns` could mean "master off, blocklist armed" or "master on, blocklist not armed", and nothing on disk could tell them apart. Studio therefore had to *guess* the master back from the flags (`allowlist_enabled || blocklist_enabled || both lists empty`), and whenever the daemon held any host at all it preferred that guess over its own prefs, which did hold the real value. The result was a filter that read as disabled on every launch once you had a host with its list switch off, and the guess then republished itself as fact — turning ADR-0030's promise ("off keeps each list's armed state, ready for when the master flips back on") into a state you could reach but never return from. It was also invisible to the other frontends: `list_capture_filter` reported the folded flags, and no tool could pause the filter without disarming the lists.
- Decision:
  - **The host holds the filter as authored and the master beside it; the engine only ever sees the fold.** This is exactly how `mapLocalEnabled` already works — the authored rules stay in `HeadlessHost`, the master gates what reaches `WailoEngine`, and what the engine holds is what devices and the proxy apply. `pushCaptureFilter()` is the one place the two meet.
  - **The daemon persists both, separately.** `PersistedCaptureFilter` gains `masterEnabled`, defaulting to on so a file written by an earlier build reads back behaving as it did.
  - **The poll carries the authored filter, not the effective one.** A frontend cannot render a paused filter from the values a device is applying — it needs the armed state the master is suppressing, or it cannot show what will come back. `captureFilterEnabled` rides beside it.
  - **Studio publishes what was authored and stops folding.** It no longer derives the master, and `CaptureFilterStore` drops from source of truth to what `MapLocalStore` already is: a local copy whose only job is re-seeding a daemon that genuinely has nothing.
  - **The lists and the master are published in one call.** `set_capture_filter` carries an optional `enabled`; null means "leave the master alone", which is what a list-only edit from the CLI, the menu bar, or an agent means. Two calls would be a state nobody authored — the daemon holding this edit's lists beside the previous master — and it is observable, because `DaemonClient` publishes each half to the flows a frontend renders from as soon as its own call returns. Studio adopts what the daemon reports, so it would take that intermediate back as intent and republish it: on the re-seed path, a stored master of off comes back on, which is this ADR's own bug with the sign flipped. `HeadlessHost.updateCaptureFilter` therefore applies both under one lock and pushes once.
  - **The CLI and MCP get the master as its own verb** (`set_capture_filter_enabled`), and `list_capture_filter` reports it. ADR-0066's test is what forces this: a master that only a window can flip does not qualify as daemon state, and the capture filter was the one master an agent could not pause without destroying the lists to do it.
- Alternatives considered:
  - **Keep the master in Studio's prefs and stop the daemon snapshot from clobbering it:** roughly fifteen lines, and it would have fixed the visible symptom. Rejected because it leaves the fact in the one place that only exists while a window is open, against invariant #2 and ADR-0059 — a CLI or MCP session would still see a filter it could not pause, and two Studio profiles against one daemon would disagree about whether the filter was on.
  - **Add the master to the device-facing `CaptureFilter` protobuf:** rejected. A device does not have a master; it has a filter to apply. Putting a frontend's feature switch in the wire contract every SDK reads would make each device responsible for resolving it, and would be a `protocol` change (with two SDK implementations to match) for something the daemon can resolve once.
  - **Infer the master from the lists more cleverly — say, treat "hosts present but both lists off" as paused:** rejected as the same guess with a different heuristic. Both readings are legitimate states a user can author, so no rule over two booleans recovers a third.
- Consequences:
  - Protocol version 11. `PollResponse` gains `captureFilterEnabled`, its `captureFilterBase64` now carries the authored filter rather than the pushed one, `CaptureFilterRequest` gains an optional `enabled`, and `set_capture_filter_enabled` is a new command. Old frontends do not speak it — see the daemon-restart note in `.cursor/rules/gradle-build-directories.mdc` before rebuilding against a live one.
  - A daemon upgraded from the previous build reads its stored file with `masterEnabled` defaulted on, so a filter that had been paused comes back live with its lists armed as stored. That is the safe direction to be wrong in — a visible filter you can switch off, rather than a filter silently doing nothing.
  - `list_capture_filter` and `set_capture_filter` now answer with `enabled` alongside the two lists, so an agent reads back the panel the user is looking at rather than the values in flight to devices.
  - The proxy needs no change: `ProxyRuleBridge` reads `engine.captureFilter`, which is the folded value, so pausing the master stops filtering both capture paths at once (ADR-0072's shared-rule test still holds).
  - Manual smoke (two-tier verification): add a host to either list, arm the list, and turn the master off — devices capture everything again while the list stays visibly armed. Quit Studio and reopen: the master is still off and the list is still armed. Turn the master on: filtering resumes with exactly the hosts that were there. With Studio closed, `wailo-cli list_capture_filter` reports the same `enabled` and the same lists, and `set_capture_filter_enabled --on|--off` moves what Studio shows on the next poll.
