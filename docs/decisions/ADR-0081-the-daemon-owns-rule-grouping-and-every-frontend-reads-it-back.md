# ADR-0081 — The daemon owns rule grouping, and every frontend reads back the layout it wrote

- Status: Accepted; the model is `daemon/DaemonRuleGroups.kt`, the wire is protocol version 10, and the panel, MCP, and CLI all address groups by id. `cd studio && ./gradlew :daemon:test :cli:test :mcp:test :desktopApp:test` is green (`DaemonRuleGroupsTest` 13, plus group cases in `DaemonIntegrationTest`, `DaemonFixturesStoreTest`, `ParseArgsTest`, `WailoMcpServiceTest`, and the new `DaemonLayoutAdoptionTest`).
- Context: ADR-0061 put rules on the daemon but kept the *grouping* out of it, as a Base64 blob Studio wrote and read and the daemon only stored. That was the right call at the time — the codec is a `shared` type and the daemon must not depend on `shared` (invariant #2) — but it left two copies of the same library with different shapes, and the daemon holding the one that could not describe where a rule sat. The consequences surfaced together: a rule an agent wrote through MCP appeared in the daemon's flat list but nowhere in the panel, because Studio's adoption path saw a layout it already had and returned early rather than merging into it; the group an agent named could not exist, since the only thing that could create one was a window; and `list_map_local` answered with a flat list that did not match what the user was looking at, so agent and user could not talk about the same panel. Grouping is not decoration — a group carries a switch that gates every rule under it (ADR-0026/0030), so "which group is this rule in" is part of what matches, and it was being decided by a frontend.
- Decision:
  - **The daemon holds the layout — groups, names, switches, and order — and it is the only copy that matters.** ADR-0059's test decides it: what AI tools may reach is daemon state, and a group's switch changes what matches, so a feature that only works with a window open is not a feature the daemon can serve. The blob is gone from the protocol and from the daemon's files.
  - **The daemon gets its own types rather than importing `shared`'s.** `DaemonRuleGroup`/`DaemonRuleNode<T>` mirror `RuleGroup`/`LayoutNode<T>` the same way `MapLocalRuleDto` mirrors its rule. This is what ADR-0061 refused, and the refusal still holds: what it refused was the daemon depending on `shared` or decoding a UI codec, not the daemon knowing that rules are grouped. Duplicating a three-field record is cheaper than the alternative, and unlike the blob it makes the daemon able to answer questions about its own state.
  - **A tree, not a flat list with a group tag on each rule.** The flat form cannot represent an empty group, and Studio creates one before it is named — a representation that describes a group only through its members would delete it between those two steps. It also makes order a derived property rather than the thing that is stored, and order *is* the match priority (ADR-0026).
  - **The daemon resolves a group's switch on the way to the host; the rule's own switch is what is stored.** `effectiveEnabled(rule, group)` is applied when nodes are compiled to host rules, so what the engine matches on is right with no window open. Sending the resolved value instead would lose the rule's remembered state, and turning a group back on would silently enable rules the user had left off.
  - **Groups are addressed by id, and an unknown id is an error.** `set_map_local --group-id checkout` on a daemon with no `checkout` group fails and says to create it, rather than inventing a group under a guessed name — which would leave two groups with the same intent and different ids, one of them invisible to whoever named the other. Creating a group is its own call (`set_rule_group`), so an id is either something you made or something you read back from `list_rule_groups`.
  - **A rule that already exists keeps its place; a new one lands last.** An agent correcting a body must not change which rule wins a match, and an automated write must not shadow a rule the user is relying on — the same priority rule an import follows (ADR-0080).
  - **Removing a group keeps its rules, unless you ask for them.** They fall back to loose rules in place, so the destructive form is the one you have to type (`--with-rules`). Removing the last rule from a group leaves the group: deleting rules is not deleting the group.
  - **Studio adopts the daemon's structure and keeps its prefs as a seed for one case only** — a daemon whose layout is genuinely empty, which is a first run against a fresh state directory rather than a delete (Studio's own deletes publish before the adoption path ever sees them). That path is also the upgrade: a pre-0081 daemon comes back with its rules loose, and Studio's own prefs — written from the same structure the blob encoded — hand the grouping back on the next attach.
  - **Studio still owns what the wire cannot carry.** A rule served from the user's own file is identical over the wire to one typed into the editor, so on adoption a rule Studio already knows keeps its `inline`/`filePath` and only takes new bytes when they actually changed. That is what stops a round trip through the daemon from severing the edit-the-file loop.
  - **The echo signature covers the groups, not just the rules.** Renaming a group or switching it off changes no rule; a signature over the flattened rules would call that "no change" and the panel would never adopt it — the exact class of bug this ADR exists to fix, reintroduced one layer up.
  - **The daemon serializes each family's edits.** The authored copy moved up from the host, and with it the read-modify-write that the host's per-family mutex used to protect; two frontends writing at once would otherwise drop one of the two rules.
  - **The daemon-less MCP backend refuses group operations out loud** rather than dropping the placement. A rule that quietly landed loose would read back as correctly filed on the next list, which is worse than an error.
- Alternatives considered:
  - **Teach Studio to merge an MCP write into the layout it already has:** the smallest fix, and it was the first idea. Rejected because it treats the symptom: the daemon still could not say where a rule sat, so `list_map_local` would still disagree with the panel, an agent still could not create a group, and the merge would be a second placement policy living in a frontend — one that only runs while a window is open.
  - **Move `shared`'s layout codec into the daemon (or a module both can see):** rejected, as it was in ADR-0061. The codec is a UI-shaped, positional format tuned for a primitive key-value store; the daemon needs the *model*, not that encoding, and taking the encoding would drag `shared`'s rule types across a boundary that exists to keep the daemon UI-free.
  - **Keep the blob and add a parallel group table:** rejected as a third copy of the same fact, with nothing to keep the two in agreement and no answer to which one wins when they disagree.
  - **Let the daemon create a group when an unknown id is named:** rejected — see the decision above. Convenient in the one-off case, and it makes a typo permanently invisible.
  - **A group id that is also its name:** rejected. Renaming a group would then move every rule in it, and two panels could not have a group called "Checkout" for different things.
- Consequences:
  - Protocol version 10. `PollResponse` carries `mapLocalNodes`/`breakpointNodes`/`seedNodes` and the `*Layout` blobs are gone; `replace_*` takes nodes; `set_rule_group`, `remove_rule_group`, and `list_rule_groups` are new commands, and the three `upsert_*` requests take an optional `groupId`. Old frontends do not speak it — the handshake already gates that, but see the daemon-restart note in `.cursor/rules/gradle-build-directories.mdc` before rebuilding against a live one.
  - `daemon/DaemonRuleGroups.kt` holds the whole model and is pure: placement, removal, group upsert/remove, flattening, and `effectiveEnabled`. It is generic over the rule type, so Map Local, breakpoints, and seeds share one implementation and cannot drift — the reason the three families behave identically here without three copies of the rules.
  - The daemon's fixture files gain `nodes` and keep reading the old `rules` field, so an upgrade does not read as an empty configuration and erase itself on the next write.
  - MCP gains `set_rule_group` / `remove_rule_group` / `list_rule_groups` and a `group_id` on the three rule tools; `list_map_local`, `list_breakpoints`, and `list_seeds` now report each rule's group and the panel's groups, so an agent reads back the panel the user is looking at. The CLI gains the same three commands plus `--group-id`, `--family`, `--name`, and `--with-rules`.
  - `shared`'s layout codecs stay exactly as they are. They are now Studio's local cache format rather than a wire format, which is the job they were designed for.
  - ADR-0080's archive is unaffected: it snapshots the panel's layout, and the panel's layout is now the daemon's. An import still lands through the panel's change handler and publishes from there.
  - Manual smoke (two-tier verification): with Studio open on a Map Local panel that has at least one group, ask an agent (or run the CLI) for `list_rule_groups --family map_local` — the ids and names should be the ones on screen. `set_rule_group --family map_local --group-id <existing> --off` → the group's switch flips in the panel within a poll and its rules stop matching, while each rule's own switch stays where it was; back `--on` restores exactly what was there. `set_map_local --id agent-1 --url-pattern … --group-id <existing>` → the rule appears inside that group, at the bottom, and serves. Repeat with a misspelled group id → it fails and names the remedy, and no rule is created. `remove_rule_group --group-id <existing>` → the group disappears and its rules remain as loose rules in place; with `--with-rules`, they go too. Create a group in Studio and leave it unnamed and empty, then quit and reopen Studio → it is still there. Quit Studio entirely, write a rule and a group from MCP, reopen → the panel shows both. Finally, upgrade check: with a daemon and prefs written by the previous build, start this one → every rule is still there and the groups come back once Studio attaches.
