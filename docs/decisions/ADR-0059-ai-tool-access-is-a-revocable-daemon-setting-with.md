# ADR-0059 — AI tool access is a revocable daemon setting with redaction on by default, and the control port is discovered

- Status: Accepted; implemented in `daemon`, `mcp`, `cli`, and the Studio Settings panel.
- Context: ADR-0058 made the daemon the sole owner of capture and left MCP a thin stdio adapter, so whether an agent can drive Wailo is decided entirely by the AI client's config file. Two gaps followed. First, there was no user-visible control: any process able to read `~/.wailo/daemon.token` had full authority over capture, Map Local mocks, and breakpoint decisions, with nothing to revoke short of stopping the daemon. Second, tools returned captured headers and bodies verbatim, so a live bearer token or session cookie travelled into a model context — and from there into a provider's logs and the user's chat history, where revoking it is nobody's job. The desktop capture tools that offer this at all solve the first with a toggle in the app, but only because their MCP server runs *inside* it; copying that would reintroduce the frontend ownership ADR-0058 removed. Separately, the fixed control port 8898 had no fallback: an unrelated process holding it left every frontend unable to reach the daemon.
- Decision:
  - **Access is a gate, not a lifecycle switch.** `mcpAccess` is daemon state persisted in `daemon.properties`, defaulting to on. When off, *every* MCP tool — `status` included — is refused with an error naming both remedies. Refusing `status` too is deliberate: a gate that still reports the LAN address and exchange counts has been narrowed, not closed. Capture keeps running, and Studio and the CLI are unaffected; the daemon remains the only process that owns capture, so nothing here depends on Studio being open.
  - **Redaction is on by default and applies at the last hop.** `mcpRedactSecrets` (also daemon state, default on) strips credentials from what MCP returns: credential and cookie headers, sensitive query parameters, and body fields whose key reads as a secret. Values are replaced with `<wailo:redacted>` rather than dropped, so an agent can still see that a request was authenticated. It lives in `mcp`, not `engine`: Studio's own UI must keep showing real values, because reading them is the point of a proxy.
  - **JSON bodies are redacted structurally.** `mcp` parses captured JSON and rewrites the tree, so a secret nested under an innocuous name is caught and a sensitive key hides its whole subtree; form-urlencoded bodies are rewritten pairwise. Redaction runs before the body byte limit is applied, so a limit cannot cut a body into something unparseable. Text that claims JSON but does not parse (usually truncated at the source) and mentions a sensitive key is withheld whole rather than passed through. Binary bodies are a known gap: a token we cannot locate is left alone.
  - **The redaction marker means "unchanged" on the way back.** `resume_hold` replaces the whole header list, so an agent that read a redacted request and echoed its headers would otherwise send the placeholder as the real Authorization value and break the call it was debugging. A header whose value still carries the marker is restored from the hold.
  - **Both settings are reachable from every frontend.** Studio exposes them as an "AI tool access" section in Settings (the second row appears only when access is on, since it is inert otherwise); `wailo-cli set_mcp_access` / `set_mcp_redaction` set them headlessly and `wailo-cli status` reports them. The daemon is the single authority — no desktop-side store mirrors either value, so a headless MCP session and an open Studio always agree.
  - **The control port is OS-chosen and advertised.** The daemon binds port 0 and publishes `{controlPort, protocolVersion, token}` in owner-only `~/.wailo/daemon.json`, replacing the bare `daemon.token`. One file means there is no window where a client can read a port without its matching token. Clients re-read it per request, so a restarted daemon on a new port needs no client restart. `wailo-cli --control-port` is gone: naming a port is now an error rather than an override.
  - **A file lock keeps the daemon single.** The capture-port bind used to arbitrate launch races on its own, which no longer holds once the control port is auto-chosen: two daemons started against different capture ports would both bind and the later one would overwrite the handshake, orphaning the earlier one. The daemon takes an exclusive lock on `~/.wailo/daemon.lock` before binding or writing anything and exits quietly if it is held. The OS releases it on crash or kill, which a pid file would not.
  - **The state directory is overridable so the singleton is testable.** Handshake, lock, settings, and log all resolve through one `WAILO_HOME` lookup that falls back to `~/.wailo`. Because the daemon is a singleton keyed on that directory, an end-to-end run against the default would attach to whatever daemon the developer already has open and rewrite its settings; a scratch directory gives the run its own daemon and its own fresh-install defaults. The launcher passes its environment to the daemon it spawns, so one variable covers both ends and no frontend grows a flag.
- Alternatives considered:
  - **The prevailing model — the desktop app hosts the MCP server and a toggle starts it:** rejected — it makes the GUI the owner again, so MCP cannot work in CI or an Appium run, and it reintroduces "is the app running?" as the first failure mode. The products built that way need launch and quit tools to work around it.
  - **Default the gate to off:** rejected — the first tool call of every fresh install would fail, and the switch's job is to revoke, not to onboard.
  - **Regex-only body redaction, avoiding a JSON dependency in `mcp`:** rejected — it cannot handle escaped values or nested objects, so secrets one level down would survive.
  - **Redact in `engine` so every frontend benefits:** rejected — it would blind Studio's inspector, which exists to show exactly these values.
  - **A read-only MCP mode instead of an on/off gate:** deferred — the tool annotations already mark which tools mutate, and a third state is worth adding only once someone wants it.
  - **Keep the fixed control port and fail loudly on a conflict:** rejected — the conflict is with software Wailo does not control, and a discovered port costs one file the daemon already had to write.
- Consequences:
  - Turning access off leaves an already-running agent's next tool call refused mid-conversation; that is the intent, and the error text tells it what happened.
  - An agent reading `<wailo:redacted>` cannot recover the value through any tool. Debugging a signature or token mismatch means turning redaction off deliberately, or reading it in Studio.
  - Redaction is heuristic on key names. It over-redacts a non-secret field whose name reads like a secret, and it cannot find a credential in a binary body.
  - `~/.wailo/daemon.token` is obsolete; a daemon and frontend across this change do not find each other and the newer frontend launches a daemon that republishes the handshake.
  - `McpAccessAndRedactionTest` proves the gate refuses every tool including `status`, that real captured traffic comes back redacted, that turning redaction off returns the real values, and that echoed placeholders do not overwrite live headers. `DaemonIntegrationTest` proves both settings outlive the client that set them, persist to the settings file, and that a client reaches an OS-chosen port it was never told.
  - Verified end to end against the installed binaries under a scratch `WAILO_HOME`: a fresh state armed and redacting, an OS-chosen owner-only handshake, a live stdio adapter refused and restored across `set_mcp_access` without a restart, and a second daemon standing down on the lock.
