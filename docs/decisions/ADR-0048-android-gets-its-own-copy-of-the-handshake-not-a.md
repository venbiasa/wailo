# ADR-0048 — Android gets its own copy of the handshake, not a shared one — and the pairing key lives in the Android Keystore

- Status: Accepted; implemented in `sdk-android`. `./gradlew :sdk-android:testDebugUnitTest` is green. Closes the Android half deferred by ADR-0039/0040, and applies ADR-0046 and ADR-0035's resolution order to Android.
- Context: ADR-0039 shipped the Wi-Fi handshake on the desktop and on iOS and deferred the Kotlin half, which left Android in a strange state: admitted over loopback because `adb reverse` is exempt, and refused over Wi-Fi with nothing the user could do about it. Android also had no discovery, no way to point the SDK at a desktop, and nowhere to put a long-term key — everything ADR-0035 gave iOS. The awkward part is that Kotlin was already the language of two of the three ends (`engine` and `sdk-android`), which makes "share the crypto" look obvious.
- Decision:
  - **`sdk-android` gets a third, independent implementation of the primitives, kept honest by shared test vectors rather than shared code.** Moving `WailoCrypto` into `protocol` would let the SDK reach it, but `protocol` is the wire format and nothing else (invariant #1); widening it to "wire format plus a crypto library" makes the one module everything depends on the place key derivation lives. The three implementations already have to agree with `sdk-ios`, which is Swift and can never share code with any of them (ADR-0010) — so cross-implementation agreement is a property tests have to hold up regardless, and a fourth copy of the vectors is cheaper than a wrong dependency.
  - **PBKDF2-HMAC-SHA256 is hand-rolled over `Mac`.** The JCE name for it arrives at API 26 and `minSdk` is 24, so the platform one would throw on the oldest quarter of the range — and pulling in a crypto library for one KDF is exactly the dependency weight invariant #3 forbids. `Mac` has been there since API 1, and the construction is a dozen lines. A test asserts it against the JVM's own implementation, so the shortcut cannot drift.
  - **The long-term key is sealed with an Android Keystore AES key; everything else is plain preferences.** The key is the one secret the device holds — anything that can read the file could impersonate this device to the Studio it paired with. `SealedKeyValueStore` wraps a `SharedPreferences` in AES-GCM under a Keystore alias, which is the counterpart to iOS's Keychain. The pinned address and device id stay unsealed: they are not secrets, and sealing them would make a Keystore failure cost more than it protects.
  - **Trust is re-read on every connect attempt, not captured when the client is built.** ADR-0046's Wi-Fi bug is a design mistake, not an iOS one, so the Kotlin client was written without it from the start: `nextAttempt` re-resolves the endpoint, the pairing and the session counter each time round the loop.
  - **Discovery is `NsdManager`, and it may only *re*-connect.** Android's own mDNS client needs no third-party library and no `MulticastLock`, because resolution happens in the system daemon. As on iOS, a discovered desktop is only dialled when this device already holds a live key for it (ADR-0040) — reaching a new one is always deliberate.
- Alternatives considered:
  - **Move the crypto into `protocol` and share it with `engine`:** rejected — see above. It trades a duplicated 200 lines for a permanent widening of the repo's most-depended-on module, and buys nothing for `sdk-ios`.
  - **Raise `minSdk` to 26 for `PBKDF2WithHmacSHA256`:** rejected — an interception SDK that a host app cannot adopt because of its `minSdk` is not adoptable, and the workaround is small and testable.
  - **Use Jetpack Security (`EncryptedSharedPreferences`) instead of touching the Keystore directly:** rejected — it is a transitive dependency tree in an artifact that ships inside third-party apps, for an AES-GCM wrap that is thirty lines against `javax.crypto`.
  - **Skip discovery on Android and require a typed address:** rejected — DHCP moves the desktop, and re-typing an IP is the thing discovery exists to avoid. The restriction to already-trusted identities is what makes it safe.
- Consequences:
  - `WailoStatus` gained `handshakeWaived`, set by the connect loop from the same `isLoopback()` the client uses to choose between `AuthRequest` and `Hello`. The panel cannot re-derive it — that needs name resolution — and a panel that guessed would tell someone their traffic is authenticated when it is not.
  - `Wailo` became the process-global control surface (`status`, `setHost`, `pair`, `forget`, `retryAfterRefusal`, `accept`/`rejectIdentityChange`). It has to be static: the panel is a separate artifact with no handle on whatever the host app did with its client, and auto-instrumentation gives the host no construction site to hold one either.
  - `FakeStudio` reimplements the desktop's admission in the test source set, so the handshake is exercised end to end over a real WebSocket rather than against a stub that admits everything — which is the failure ADR-0046 records.
  - Sealing and sending are serialised behind a mutex. A sealed frame's sequence number is assigned at seal time, so two frames sealed in order could otherwise reach the wire reversed and the far end would read the lower one as a replay and drop the session.
  - Manual smoke: with `adb reverse` in place → connects with no pairing, and the panel says so. Remove the reverse, put both on the same Wi-Fi and type Studio's address → trusted on first contact, and the session is sealed. Background the app for a minute and reopen → it reconnects on its own (the ADR-0046 regression). Turn on "allow only paired devices" in Studio and Forget the device there → the panel latches a refusal rather than retrying; scan the QR → it pairs and reconnects.
