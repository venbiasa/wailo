# ADR-0067 — The daemon owns the seed library and spends it, so Seeds reach CLI, MCP, and the menu bar

- Status: Accepted; implemented as a seed library + armed queue on `HeadlessHost`, `replace_seeds` / `upsert_seed` / `remove_seed` / `set_seeds_enabled` / `fill_seeds` / `clear_seed_queue` on the daemon, `seeds.json` beside the other fixtures, six `wailo-cli` verbs, seven MCP tools, and a `Seeds` row in the menu bar's `Enable Tools`. Studio keeps the grouped layout and the body files and publishes a flattened projection, exactly as it does for Map Local. Control protocol bumped to 6. Verify with `cd studio && ./gradlew :host:test :daemon:test :cli:test :mcp:test`.
- Context: A seed was the one interception feature only Studio could use. ADR-0041 put the spend on the desktop because a hold was already a desktop round-trip, and every consequence followed from that: the bodies stayed in Studio's app-data files, the armed queue lived in a Compose `remember`, and ADR-0066 had to leave Seeds out of the menu bar because there was no daemon state to draw. Meanwhile the frontends that most want a scripted answer — a CLI run, an agent driving MCP — can already set the breakpoint that creates the hold, and then have nothing to answer it with. The premise had also quietly expired: since ADR-0058 the hold is not a desktop round-trip at all, it is a *daemon* round-trip that Studio happens to be watching.
- Decision:
  - **The daemon owns the seed library, bodies included.** A `HostSeed` carries its bytes rather than resolving them through a callback, because the daemon has to answer a hold with no Studio to ask. That is the one real departure from Map Local, whose bodies stay on the desktop precisely because the *device* serves them.
  - **The daemon spends seeds; no frontend does.** One spender, in `host`, on the process that owns the engine. A seed answers exactly one hold whether the answer was triggered by Studio's Fill button, `wailo-cli fill_seeds`, or an MCP tool — which is the only way an ordered sequence means anything with more than one frontend attached.
  - **The library is durable; the armed queue is not.** The library is authored configuration and persists like Map Local and breakpoints (ADR-0061). The queue is a position in a run, so it dies with the daemon — restoring a half-spent sequence into a script whose first half never happened is worse than starting over (ADR-0041, unchanged).
  - **Writing a seed does not arm it.** `set_seed` builds the library, `fill_seeds` starts the sequence and sweeps the holds already waiting (ADR-0044). Keeping them separate is what lets a run configure ten seeds and then decide when the clock starts.
  - **The daemon publishes its triage verdict, and that is what opens Studio's window.** A hold the daemon has decided about and not answered is one that needs a human. Studio waits for that verdict instead of opening on first sight, or every seed-answered hold would flash a window open on its way past.
  - **Seeds get a menu bar row.** ADR-0066's rule stands — a row exists only if the daemon owns the state — and Seeds now qualify. The carve-out was about ownership, not about Seeds.
- Alternatives considered:
  - **Leave the spend in Studio and give the CLI/MCP a way to ask it to run:** rejected — it makes an interception feature depend on a window being open, and turns a scripted run into a request to a UI that may not exist. It also keeps two spenders alive the moment a second frontend attaches.
  - **Keep the bodies in Studio and have the daemon fetch them at spend time:** rejected — the daemon would have to block a held device on a round-trip to a frontend that is allowed to be absent, and "no Studio" would read to the device as a hung request rather than an unanswered hold.
  - **Push seeds to the device like Map Local rules:** rejected — a seed answers a hold, and a hold exists precisely because the device handed the exchange over. Sending the answer back as a rule would race the hold it is meant to resolve.
  - **Have Studio open its window optimistically and close it if the daemon answers:** rejected — a window that appears and vanishes is worse than one that appears a poll late, and it would steal focus for holds the user was never meant to see.
  - **Keep one flat seed list and drop Studio's groups:** rejected — the grouped layout is how a library of any size stays navigable, and the layout string already crosses the wire opaquely for the other two features (ADR-0061).
- Consequences:
  - The protocol bump means an updated frontend replaces an older daemon rather than misreading it (ADR-0058). `SeedResponseProvider` is gone; `spendSeedOn` reads the seed's own bytes.
  - A seed authored from the CLI or MCP appears in Studio's panel, and one authored in Studio is listable and spendable from either. Studio imports an unfamiliar library by writing the incoming bodies to its own files, so the panel can edit them.
  - A seed whose body file has gone missing is published with `bodyAvailable` false and declines the hold rather than answering it empty — the same distinction Map Local draws, now enforced at the seam instead of at read time.
  - The Seeds master stays non-destructive like every other one (ADR-0030): off, the armed queue is inert but intact, and on re-arms it — which is also when the holds that piled up meanwhile get their first look. The one place it does discard is a Fill it declines, which is the pre-existing behaviour (ADR-0041). `list_seeds` therefore prints the master above the rows, since an armed seed under a closed master is one that will not fire.
  - Manual smoke: with Studio closed, `wailo-cli set_breakpoint`, `wailo-cli set_seed`, `wailo-cli fill_seeds`, then drive the app and confirm the call is answered with the seed and `list_seeds` shows it spent. Open Studio and confirm the same seed is in the panel with its body. Author a second seed in Studio, confirm `list_seeds` sees it, and confirm the menu bar's `Seeds` row and the panel's master agree in both directions.
