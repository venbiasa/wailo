# ADR-0046 — Nothing on the device may need a relaunch to recover

- Status: Accepted; implemented in `sdk-ios`. `cd sdk-ios && swift test` is green (94). Amends ADR-0040.
- Context: Two bugs reported together, with the same shape and the same worst property. Connect over Wi-Fi, get trusted on first contact, background the app — and it never reconnects again, at any address, until Studio is told to forget the device. Separately: launch with no cable, let discovery find nothing, then plug the cable in — and USB never comes up until the app is force-quit. In both, the transport is fine, both ends are running, and the device has quietly decided it is done. A user cannot tell that apart from "Wailo is broken", and the only two workarounds either need the other machine or throw the session away.
  - The Wi-Fi one is a direct consequence of TOFU (ADR-0040) and only bites *after* it succeeds. `WailoClient` was handed the `Trust` computed when it was built, and it reconnects internally without going back through the coordinator. But a first contact changes what the peer will accept: Studio now holds a key for this device and mixes it into the auth key from the very next connection. So every reconnect re-introduced a device Studio already knew as a stranger, derived the auth key without the key it had itself just stored, and failed the mac check — silently, and identically forever, because the input that was wrong never changed. Trust-on-first-use worked exactly once per pairing, which is the one number of times that looks like it works.
  - The USB one is `WailoUsbListener` giving up. Studio reaches an iOS device by dialling a port the device listens on, so a bind that fails at launch and is never retried is indistinguishable from a broken cable. The causes of a failed bind are all temporary — an unanswered Local Network prompt, the stack not up yet on a cold launch, the port still held by the bind being replaced — and the only re-arm was a foreground notification the user has no reason to trigger while the app is already open.
- Decision:
  - **Trust is a live property of a connection, not a value frozen when the client was built.** The factory closure reads a box the coordinator owns per client, so each handshake asks again rather than replaying an answer from before the last one succeeded. `handshakeEstablished` moves the box to `.paired` — it is the only place that can, since reconnects never re-enter `apply`.
  - **The box belongs to the client it was built for, not to the coordinator.** A late callback from a client that has already been replaced then cannot upgrade the live one, which is the failure mode this shape trades for.
  - **A transport the device wants keeps trying for as long as it wants it.** The USB listener retries indefinitely with backoff from 0.25s to 15s, and a `wanted` flag so a retry scheduled before `stop` cannot rebind after it. Short at the start because the port-just-released case clears in milliseconds; capped and patient after that because the usual cause is a permission prompt no amount of retrying can hurry.
  - **One bind attempt per pass, rescheduled rather than slept through.** `bindListener` waits up to two seconds for the listener to settle and `accept` runs on the same queue, so a burst of retries is also a burst of seconds in which an inbound Studio connection cannot be answered. The previous code's 30-attempt blocking burst could hold that queue for a minute and *still* give up.
- Alternatives considered:
  - **Rebuild the client after a first contact instead of upgrading its trust:** rejected — it drops a connection that is working, at the exact moment it started working, and races the reconnect it just triggered. The value was stale, not the client.
  - **Re-enter `apply` on every reconnect so trust is recomputed there:** rejected — `apply` decides *which endpoint* to talk to, and letting a reconnect re-run it means discovery churn can move a live session to a different desktop mid-stream.
  - **Have Studio stay lenient toward a device it already trusted on first contact:** rejected — that is the property TOFU exists for. A pinned key that is not demanded is not pinned.
  - **Ask the user to relaunch when USB will not bind:** rejected — the app cannot reliably tell why a bind failed, so the message would be a guess, and the honest version of it ("try again later") is something the code can just do.
- Consequences:
  - `WailoHandshakeReconnectTests` covers the Wi-Fi half against a fake Studio that *remembers* devices, because a lenient stub admits everything and proves nothing: first contact must be admitted, and the reconnect after a dropped link must be admitted *as a keyed device*. With the upgrade removed it fails exactly as reported — the reconnect is never admitted at all. A second, socket-free test pins the mechanism: once Studio holds a key, a device that still says `firstContact` is rejected while the stored key is accepted.
  - Testing the Wi-Fi handshake at all needed two debug-only seams, both narrow: `WailoPairingStore.shared` is settable in DEBUG (the Keychain refuses generic-password items to an unsigned macOS test host — the same constraint `WailoSecretStorage` already exists for), and `WailoCoordinator.forcesWifiHandshakeForTesting` makes loopback take the Wi-Fi path, since loopback is precisely the case the handshake is skipped for and is also the only peer a unit test can dial. Without them ADR-0039/0040's entire device half was manual-smoke-only, which is how this broke unnoticed.
  - `WailoCoordinator.pairingStore` became a computed property. It is a process-lifetime singleton, so a stored reference would outlive any replacement of the shared store and the seam above would silently do nothing.
  - `testListenerRebindsItselfOnceTheBlockedPortIsFree` holds the port with a raw socket rather than another `NWListener` — the listener asks for endpoint reuse, and two sockets that both allow it share the port happily, which would make the test pass without the retry it exists to check.
  - Manual smoke: connect over Wi-Fi to a Studio that has never seen this device → trusted on first contact. Background the app for a minute and reopen → it reconnects on its own, with no Forget on either side. Force-quit and relaunch → same. Then: launch with no cable and no Studio on the network, wait for discovery to find nothing, plug the cable in → USB takes over within ~15s without touching the app. Deny Local Network permission, launch, then grant it in Settings and return → USB comes up unaided.
