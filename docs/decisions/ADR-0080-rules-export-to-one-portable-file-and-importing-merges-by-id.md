# ADR-0080 — Authored rules export to one portable file, and importing merges by id rather than replacing

- Status: Accepted; the schema and merge are in `shared`, the container and file IO in `desktopApp`, the affordance in the Map Local panel. `cd studio && ./gradlew :shared:jvmTest :desktopApp:test` is green (`RuleArchiveTest` 12, `RuleArchiveContainerTest` 8). First ADR for moving authored rules between machines.
- Context: ADR-0061 settled *where* rules live and deliberately left two copies: the daemon holds a flat projection that devices consume, Studio's prefs hold the grouped layout — groups, names, order, and inline-vs-file — that the daemon cannot decode without depending on `shared`. Neither copy can be moved, inspected, or restored: the layout is a Base64 blob inside a `java.util.prefs` plist, the bodies are opaque files keyed by generated rule id under Application Support, and the daemon's snapshot is a third place they are duplicated. A user with real work in the panel — dozens of rules and several megabytes of authored bodies — has no way to back it up, move it to another machine, or hand it to a colleague, and no way to undo a mistake. The trigger was a question about a *different* change (making an MCP-authored rule visible in the panel): touching the sync logic at all was unsafe while there was nothing to restore from.
- Decision:
  - **A second, explicitly named schema rather than reusing the layout codecs.** The prefs codecs are positional `|`-separated Base64 lines tuned for a primitive key-value store, where a field added in the middle shifts every later one and only their own legacy branches keep old values readable. Writing that blob to a file would have been ~20 lines and lossless *today*, and unreadable and version-brittle for the whole life of a file someone keeps. `RuleArchive` is instead named keys with defaults, decoded with `ignoreUnknownKeys`, so an archive from a newer Studio still imports minus only what this build cannot model, and a human can read and hand-edit it.
  - **One file carries every authored tool** — Map Local, breakpoints, seeds, and the capture filter — so what a user keeps is one artifact rather than four that drift apart. Every section is optional and `null` means *this file says nothing about that tool*, which an import leaves alone; that is deliberately distinct from an empty section, so a single-tool export can never read as "and delete the rest".
  - **Bodies travel inside the file, as their own entries in a compressed container.** An archive that referenced only the author's own paths would import as a set of broken mocks on any other machine, or after a folder move — the exact failure the feature exists to prevent. The container is a zip holding `manifest.json` plus one entry per body under `bodies/<tool>/`, named with the extension the rule's Content-Type implies.
  - **A container rather than one compressed blob**, which was the simpler way to get the same size win. Encoding bodies into the manifest costs a third of their size in Base64 *before* compression, and deflating an already-encoded PNG wins almost none of it back; as entries they stay exactly the bytes they were. It also decides what a recipient can do: a single blob can only be imported or discarded, while a zip opens with the tool their OS already ships, so they can read the manifest and open an individual mock response before trusting it. Sharing was the requirement, and a format you cannot inspect is a poor thing to be handed.
  - **Entry names are sanitized when written, not trusted when read.** Rule ids arrive as free text from the CLI and MCP, so an id containing separators or `..` would otherwise name an entry that escapes `bodies/`. Names are reduced to alphanumerics, `_` and `-`, with collisions disambiguated; on import, bodies are looked up through the zip's own index and handed to the stores, which name the files they write from the rule id — no entry name ever reaches the filesystem.
  - **Export is byte-deterministic** (entries sorted, fixed compression level), so re-exporting unchanged rules produces an identical file. That is what lets a user keep archives in version control and see only the changes they actually made.
  - **A file-backed rule carries both its path and its bytes, and the importer prefers the path when it resolves on *this* machine.** Rewriting every imported rule to a managed copy is simpler and is wrong for the author: it silently severs the "edit the file, the mock follows" loop that made them choose a file source, and re-importing your own backup would quietly convert your rules. Falling back to the embedded copy only when the path is genuinely absent serves the colleague without taxing the author. Whether a path resolves is a filesystem question, so `shared` takes it as a parameter and `desktopApp` answers it.
  - **Import merges by id and never overwrites.** A rule whose id is already present is skipped, not replaced, so an import can never revert an edit — and re-importing the same file is a no-op, which makes the operation safe to repeat when you are unsure whether it took. The cost is that restoring a rule you have since broken means deleting your copy first; silently reverting edits is the worse failure of the two.
  - **New entries append at the end**, which is the lowest match priority (ADR-0026). An import must not change what an existing rule matches, and prepending would let a colleague's rule shadow yours on the next request.
  - **Groups merge by id too:** a group already present takes the incoming rules it doesn't have, an unknown group arrives whole, and a group whose every rule was already here is dropped rather than added empty.
  - **The capture filter unions hosts and leaves its three switches alone.** An import contributes what someone else filters; whether this capture is filtered at all stays the user's decision. The feature masters are written into the archive for the same reason — a backup that omits them isn't a complete record — but merge does not apply them, for the same reason it does not apply anything that already has a value here.
  - **The schema, the layout conversions, and the merge are pure and live in `shared`; every byte of IO is in `desktopApp`.** That is ADR-0013's split unchanged, and it is what makes the merge — the part with the real edge cases — a plain unit test with no filesystem. `shared` names the container's entries because they are part of the format, and touches no `java.*` to do it. The container itself is split again from the body stores, so the zip is testable on hand-built contents without an app data directory.
  - **One overflow menu in the panel header, with text labels.** Export and import are the same arrow to anyone who has not learned which way round it goes, and the header already carries four controls. The result is reported as one line the host returns and the panel shows for a few seconds; the panel owns that string, so no transient status has to cross the host boundary as state.
- Alternatives considered:
  - **Write the prefs layout blob plus the bodies:** rejected — see the first decision. Cheapest to build, worst to live with.
  - **A single JSON document with bodies Base64-encoded into it:** this was built first and then replaced before it shipped. It is one file and human-readable, but it inflates every body by a third and, once compressed to be shareable, becomes a blob a recipient cannot look inside — losing the readability that was its only advantage. A container gets both. Changing it cost a schema field and a rewrite of the IO; changing it after release would have cost supporting both formats forever, which is why it was worth doing at once.
  - **Gzipping that JSON:** rejected for the same reason — it fixes size without fixing inspectability, and leaves the Base64 inflation underneath the compression where it barely helps.
  - **Replace on import:** rejected as the behaviour. It is the only thing that restores a rule you have since edited, and it is also the only thing that can destroy work by accident — including the whole panel, from a file whose contents you misremembered. Offering *both* at import time was also considered and deferred: it doubles the decision surface for a feature whose first job is to be safe, and merge can be extended with a replace path without changing the format.
  - **Exporting only the panel you are standing in:** rejected. Per-tool files are the natural reading of a per-panel button, and they are four things to lose instead of one. The schema still supports them, so this stays reachable.
  - **Putting the format somewhere `cli` and `mcp` could reach it:** deferred. `shared` is Studio's alone (a sibling of `engine`/`host`), so a headless `wailo-cli export` would need the schema in a module under both trees, or the daemon to grow an opinion about the grouped layout — which is exactly what ADR-0061 refused. Worth doing when a headless caller actually wants it; the schema is deliberately plain enough to reimplement or move.
- Consequences:
  - New `shared/RuleArchive.kt` (schema, conversions, `mergeIn`, entry names), `desktopApp/RuleArchiveContainer.kt` (the zip), and `desktopApp/RuleArchiveIo.kt` (`buildArchive`, `writeArchive`, `importArchive`). `shared` gains `kotlinx-serialization-json`; the plugin was already applied for the Navigation 3 keys. The container needs no dependency — `java.util.zip` is in the JDK.
  - Files are `.wak` and are zips. The extension names no tool on purpose: every section is optional, so one file type covers a single-tool export and a whole-profile backup alike, and a tool added later is a new manifest field rather than a second extension — a second one would also mean a second OS file-type association and an import dialog whose filter the user has to choose before finding their own file. A name like `.wailorules` (the first choice) would have expired the moment something that is not a rule went in, which Settings would do. The save dialog seeds a dated name so successive backups sit beside each other, and re-appends the extension if the user types it away — the open dialog filters on it, so a file saved without one would be invisible to the import that wants it back. The manifest's presence is what identifies the format, so a zip from anywhere else is rejected rather than half-imported.
  - Two of the six tool panels stay out. `Settings` is a candidate later, but its rows include the MCP access gate and the proxy toggles, so it needs the capture filter's treatment — contribute values, never flip a security switch. `Devices` should never be exportable at all: pairing identity is Keychain-backed credential material, and a portable file full of it is a liability rather than a backup.
  - `GroupedRuleListPage` gained a `notice` slot under the description and an `overflowActions` list, and `Common.kt` a `HeaderOverflowMenu` (with `ic_more_vert`, Material Symbols Rounded 400/0 per the icon convention). The overflow is a list the page places itself, not a composable slot the caller positions: a three-dot menu belongs last, against Close, and the existing `headerActions` slot sits up with the feature controls (the breakpoints panel's "open window" button is there). Both are generic, so wiring the same two actions into the Breakpoints and Seed panels is one call site each — not done here, because one entry point that exports everything is not made better by three.
  - `awaitNativeFileDialog` is now general (title, mode, default name, filter) instead of hard-coded to loading a body file; `chooseMapLocalFile` passes its own filter through.
  - The import routes each merged layout through the panel's existing change handler rather than assigning state, so prefs, the orphaned-body sweep, and the daemon push all run exactly as they do for a hand edit — including ADR-0061's rule that Studio's layout is the authoring copy, which now means an import lands in the daemon on the next publish.
  - The two-copy design of ADR-0061 is unchanged. This gives it the durable escape hatch it lacked, and nothing more: the archive is not a third source of truth, it is a snapshot with no live relationship to either copy.
  - Manual smoke (two-tier verification): with rules authored in groups, including one file-backed rule and one image body, open Map Local → overflow → *Export all rules…* → save. Unzip the file (Finder opens it directly): it should hold a readable `manifest.json` with your group names and rule names in it, plus `bodies/map-local/…` entries — and the image body should open as an image, at its original size rather than a third larger. Delete a rule and a whole group, then *Import rules…* the same file → exactly the deleted ones come back, appended at the bottom, bodies intact (open one in the editor); nothing else moved and no rule you kept was altered. Import the same file again → it reports that nothing was new and the panel is unchanged. Edit an imported rule's URL, import again → your edit survives. Confirm the file-backed rule still points at your own file after a re-import; then rename that file on disk, import into an empty panel, and confirm the rule comes back inline serving the archive's own copy rather than falling through to the network. Export twice without changing anything and confirm the two files are byte-identical (`shasum`). Check the breakpoints, seeds, and capture-filter panels picked up their share. Cancel both dialogs → no notice, nothing changed. Import a file that isn't an archive → it says so and changes nothing. Check the notice line in both light and dark (ADR-0016), and that it clears itself.
