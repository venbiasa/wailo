# ADR-0079 — Comparing two exchanges canonicalizes both and then diffs them as text, in `shared` where only Studio can reach it

- Status: Accepted; implemented in `shared` and shown in its own window from `desktopApp`, with each pane an ordinary `CodeEditor`. `cd studio && ./gradlew :shared:jvmTest` is green (`TextDiffTest` 21, `BodyFormattingTest` 31). First ADR for comparing two captured rows.
- Context: Studio could show one exchange at a time — `selectedId` was a single `String?` — so the question an inspector is most often opened for, *what is different between these two calls*, had no answer inside the app. The way to get one was to right-click both rows, copy each as cURL, and diff them somewhere else. The ask named the shape it wanted: "diff it like git lens" — two panes, red and green, step through the changes.
- Decision:
  - **Canonicalize each side, then run one ordinary line diff over the result.** A text diff is the familiar shape and it is what was asked for, but run naively over two HTTP messages it is useless: a server may reorder its JSON keys and its headers freely between two identical calls, and every one of those reorderings would read as a change. So the noise is removed *before* the diff rather than by teaching the diff about HTTP. Headers are sorted by name; a JSON body is parsed and re-serialized with sorted keys through `canonicalJson`. One renderer then serves headers, bodies, and the summary alike.
  - **Sorting keys is a switch, on by default.** It is the setting that makes two payloads line up, and it also moves the document away from what the server actually sent — which matters when the order *is* the question. Defaulting it on and leaving it reachable is the only split that serves both.
  - **Array order is never touched.** Position in a JSON array is meaning, not formatting, so canonicalization stops at object keys. Sorting array elements would silently hide a reordered list, which is a real bug and exactly what someone would open this to find.
  - **The diff engine lives in `shared`, which makes it Studio's alone — deliberately.** `shared` is a sibling of `engine`/`host`, so nothing on the `daemon`→`cli`/`mcp` branch can reach it, and this feature will never appear there. That does not violate the "Studio may author and display, but may not be the only place a feature works" invariant, because comparison derives nothing a client does not already hold and no behaviour depends on it: an AI tool that wants a diff calls `get_exchange` twice and diffs them itself, with no daemon state to keep in step. The alternative — a module below both trees — buys a capability nobody is missing.
  - **Each column is the app's own `CodeEditor`, over a document padded to the diff's rows.** The first cut drew the two columns as one `LazyColumn` of two-cell rows — correct about alignment, and wrong about everything else, because a diff pane is a *code viewer* and that renderer had to reimplement, badly, what the editor beside it already did. It shipped with no soft wrap (so a long JSON string ran off the right edge with no way to see it), no drag-select and therefore no copy of anything smaller than a whole side, no find, and folding that collapsed both columns on one column's brackets — which is not a cosmetic mismatch but a wrong answer, since the sides genuinely have different structure. Three rounds of fixes went into that renderer before the ask was restated plainly: *use the common code editor; the difference is only the highlighting*. That is the correct decomposition. Each side is a real document — its own text, with a blank line wherever the row belongs only to the other side — and the diff contributes what a diff actually is: row tints, inline spans, supplied gutter numbers, and a fold map. Everything else is the editor's, so it behaves here exactly as it does in the detail panel, and keeps doing so as the editor grows.
  - **What can be shared is shared; the vertical scroll cannot be, so it is mirrored.** Horizontal scroll and the soft-wrap flag are one value passed to both panes, which makes disagreement unrepresentable. Wrap has to be that way for a subtler reason than taste — a wrapped line is taller than an unwrapped one, so two panes free to differ would put row N at two different heights; that is also why the editor's per-instance wrap toggle is suppressed here and asked once, from the toolbar. The vertical position looked like the same case and is not: a `LazyListState` is not a position but a *pending delta plus a position*, and the delta is consumed by whichever list measures first, so a second list reading the same state never moves at all. So each pane keeps its own and copies the other's index and offset, which name the same place because every row is the same height on both sides. The copy is skipped when the target is already there, which is what stops the two mirrors from driving each other.
  - **The panes get an identical width, not a weight each.** A `Row` splitting an odd number of pixels hands one child the spare one — normally invisible, and here not, because the pane width decides how many monospace cells fit and therefore where a wrapped line breaks. One column reflowing a row that the other does not is a misalignment that persists for the rest of the document, from a single pixel. Measuring once and halving removes the possibility.
  - **A wrapped row is as tall as the *taller* of its two sides.** This is the one thing a lone editor cannot work out for itself, and without it soft wrap and side-by-side alignment are mutually exclusive: a line that reflows to three rows on the left and one on the right pushes everything below it out of step forever. So each pane is told the opposite side's line length for the row, wraps it at its own column count — both panes are the same width, so the count matches — and takes the larger row count. The alignment then survives wrap, which is what makes wrap usable here at all.
  - **`readOnly` is what makes an editor a viewer.** No new component, no "viewer half" extracted from `CodeEditor`: the diff passes the same flag the body preview does, and gets selection, find, folding, and scrolling without the ability to type. Extracting a shared viewer would have split the one file two surfaces must agree on into two that could drift.
  - **A run of removals immediately followed by a run of additions is paired into `Changed` rows** rather than shown as a delete block above an insert block. The pairing is what makes an *inline* highlight possible at all: without a left line and a right line on the same row, there is nothing to compare within.
  - **Within such a run, lines are paired by correspondence rather than by position.** Zipping the two runs from the top is only right when they are the same length and describe the same thing, and a JSON array that empties on one side breaks both at once: a block of lines disappears, any unrelated change below it falls into the same run, and every pair after the array is off by the length of the block. The visible result is an array element's `{` reported as having "changed into" a property several lines further down, the genuine change opposite it demoted to a plain deletion, and the whole tail of the object tinted. So a line with no plausible partner opposite steps aside as a one-sided row instead of consuming a pair and dragging the rest of the run with it.
  - **Correspondence is indentation first, then shared text at the ends.** Depth is the cheap structural signal and it is the one that resolves this case outright — an array element's brace is never a property of the object containing it, whatever else they have in common. Shared prefix and suffix then carry the rest, because that is where a key lives: `"page": 1,` and `"page": 2,` share nearly everything, while `],` and `"page": 2,` share only an indent and a comma. Where neither side has a partner in reach, the two are paired anyway — that is the ordinary "these lines were replaced" case, and it is what keeps the inline highlight working.
  - **The alignment is bounded by how *different* the two sides are, not by how large they are.** The first cut filled an n×m table and refused to align at all above a cell count, falling back to a wholesale replacement. That criterion is inverted. Two captures of one endpoint run to thousands of identical lines around a handful of changed ones — the largest inputs are the *easiest* to align — and the cap fired on precisely those: a 4000-line body whose two changed fields sat at opposite ends survived head/tail trimming with a 4000-line core, blew the cell budget, and was reported as 4000 differences. The whole feature read as "everything below the first change is different", and the earlier trailing-comma and correspondence fixes never ran, because both live past that early return. Aligning by Myers' algorithm instead costs O((n+m)·D), so the bound goes on D: near-identical bodies settle in a few steps at any length, and only genuinely unrelated documents fall back. The number itself is then set by the one real constraint — the recorded trace is `(D+1)²` ints — rather than by a guess about payloads, because a guess is what failed twice: two records of the same shape but different content (4142 lines against 2032, 82 change regions) sit at distance 2900, which a cap chosen for "typical" traffic had already excluded. Where even that is not enough the answer is Myers' linear-space refinement, which needs no trace at all, not a bigger constant.
  - **The inline span widens out to token boundaries.** Between `"total": 1200` and `"total": 1900` only one character actually differs; marking that character is technically right and unreadable. Marking `1200` against `1900` is what the eye can use.
  - **Request/response and headers/body are flattened into one tab row**, not a side toggle crossed with a tab strip. The answer is almost always "the response bodies", and one row of tabs reaches it in a click instead of two. `Summary` takes the slot a Raw tab would have had, and splits the URL's query parameters onto a line each — so one changed parameter is one changed line rather than two unreadably long URLs.
  - **The second row is picked from the selection, through the row context menu.** The selected row is A; "Compare with selection" on any other row makes it B, and unticking it ends the comparison. This reuses the seam Map Local, Seed, and Breakpoints already author rules through, rather than introducing a multi-select mode to the list — and it means the compare state is two ids, so "two rows selected but not being compared" is not reachable.
  - **The diff is a separate OS window, following the breakpoint inspector (ADR-0034).** It was first built into the detail panel below the list, and that was the wrong shape: two monospace columns in a strip 180–360dp tall had room to prove the diff worked and none to actually read it, and every dp given to the diff was taken from the list. A window is the only place two full-height columns fit. It costs a window lifecycle, which ADR-0034 has already paid for and shown to be worth it.
  - **The pair is pinned to the window, so the comparison outlives the selection that started it.** Inline, the natural rule was "A is the selected row", which meant clicking any other row silently ended the comparison — tolerable when the diff *was* the selection's panel, wrong once it is its own window, since the reason to compare two calls is usually to keep hunting through the rest. So opening the window freezes `(A, B)` and the list behind it is fully usable. It follows that swapping trades the window's own two ids and never touches the selection, and that the two compared rows need a mark of their own rather than borrowing the selected row's fill.
  - **The window is the only place a comparison happens** — the inline panel was removed rather than kept as a second mode. Two renderers of one diff is two things to keep in step for a view the ask already called unreadable.
  - **Each side's header carries only what tells the two apart.** The first cut showed status, method, and URL — every one of which is identical on both sides in the usual case, two calls to one endpoint, so the header answered "what are you comparing?" with the one fact the user already knew. The second cut over-corrected and added a whole line of clock time, duration, and response size: facts that always differ, so marking them marks every comparison, and that are already in the row in the main list. Both are gone. What is left is a second line that appears only when there is something on it.
  - **Fields that differ between the two sides are emphasized, and the ones that only matter when they disagree are shown only then.** Which app, which device, and which capture path are noise when comparing two calls from one app, and the whole story when they are not — so they appear only when they differ. Time is never emphasized: two captures always differ in it, so marking it would mark every comparison.
  - **The window opens on the first section either side has content for,** rather than always on `Resp Body`. A pair of `204`s or two GETs whose bodies were dropped by a capture filter would otherwise open on "Nothing to compare" over two exchanges that differ plenty. Decided from the body handles' declared sizes, which are known at composition — the bytes arrive later (ADR-0069), too late to choose a tab with.
  - **Both bodies are fetched as the same bounded prefix every other surface uses, and the panel says when it hit the ceiling** (ADR-0069). Two bodies that agree for the first 8 MB and diverge after would otherwise be reported as identical, which is the one wrong answer this feature must never give.
  - **One hue for "these differ", not a red side and a green one — and so no `-`/`+` in the gutters either.** Red-against-green states a *direction*: this was removed, that was added. A comparison has none. A and B are two captures, either may be the older, and the Swap button proves it — swapping inverts every color in the view while the two payloads mean exactly what they did before. The information the second hue looked like it carried is already carried better elsewhere: which side a line is missing from is said by the filler band opposite it, which is unambiguous and needs no legend. Dropping the pair also frees the choice of the one remaining hue, which is what lets it dodge the syntax palette (below), and it empties the gutter for the fold arrow. The tint reuses `warning` — the "look here" token, not the "this is broken" one — keeping the semantic-token reuse the URL highlighter established, so both schemes come free and `tokens.json` gains nothing (ADR-0013/0016).
  - **The row tint stays faint, and the inline span resets the text under it to plain `onSurface`.** The first cut tinted added rows with `success`, which is also the JSON highlighter's string color: a changed string value was drawn in green on a green background, unreadable no matter what its contrast ratio computes to, because two greens do not separate by hue. Alpha alone cannot fix that, so the strong tint and the syntax color are never allowed to coexist — inside the changed span the token color is dropped, and everywhere else the tint is kept light enough that any token color survives on it. This is what makes the single hue's identity a free choice rather than a constraint: the span no longer carries syntax color at all, and a faint row tint is legible under any of them.
  - **A JSON line's trailing comma is not part of its identity.** Pretty-printed JSON puts the comma at the end of the line it follows, so whether a property carries one is decided by whether anything comes *after* it in its object — a fact about its neighbours, not about itself. Compared literally, appending a key to an object reports its previous sibling as changed too, and because that one mismatch can leave the LCS with no common line to anchor on, the whole block then pairs up index-wise and every property in it reads as changed. So the alignment matches on the line with a structural trailing comma removed, while each side still displays its own text. This is the payoff of knowing the body is really JSON: the normalization is only correct because [canonicalJson] escapes control characters, which means no string literal spans or ends a line and a final `,` is therefore always punctuation.
  - **The normalization is an alignment key, not a rewrite.** `diffLines` takes a `key: (String) -> String`, so what is *compared* and what is *shown* stay separate — the comma is still on screen, and a row whose sides differ only by it is simply not marked. Rewriting the text instead would have made "Copy A" emit JSON that no longer parses.
  - **JSON-ness is sniffed from the bodies, not assumed from the tab.** "This is the response body" and "this is JSON" are different claims, and conflating them made the panel offer key sorting on an HTML document — a control that could not do anything — and paint that document's quoted attributes with the JSON highlighter. Both now hang on the same `bodyContent` decision the rest of the app formats bodies by, and when it says no the sort control goes disabled and names what the body actually is, rather than silently doing nothing.
  - **Each side's URL wraps instead of ellipsizing.** The tail of a URL is where the id that tells two calls apart usually lives, so truncating it removes the one field being compared. That in turn forced the seam between the two header strips to be *drawn* rather than laid out: a `ColumnDivider` sizes itself with `fillMaxHeight`, which is what has to be pinned by an `IntrinsicSize.Min` row, and that pin is incompatible with text that decides its own height by wrapping.
  - **Folding splits in two: the arrow is per side, the span is shared.** These look like one decision and are not, which is why the first cut got it wrong in both directions at once. *Where a block opens* is a fact about one document — an array populated on the left and `[]` on the right opens a block on the left only — so scanning the merged rows put an arrow in the right gutter beside a blank filler, a control over nothing. But *what collapsing hides* cannot be per side, because hiding four rows in one pane and one in the other slides the columns apart, which is the single thing the row grid exists to prevent. So each pane's arrows come from its own document's brackets, while the span every arrow collapses runs to whichever side closes later. Both panes still carry a control for a block either has, so a fold can be worked from whichever column is being read.
  - **The bracket scanner is the editor's, used twice, not a diff-shaped copy of it.** There was a second implementation that walked `DiffRow` pairs; it existed only because the diff had its own renderer, and it was a second place for "which brackets are foldable, and which are inside a string literal" to drift. Padding each side into a real document means `computeFoldRegions` — the editor's own, already covering escapes and string literals — answers for both, and the diff merely merges the two answers.
  - **Stepping to a change opens whatever is collapsed over it,** and the change counter is computed over every row rather than the visible ones. Counting only what is on screen would make folding a block look like it made the changes inside it disappear; revealing on arrival is the same rule the code editor's find already follows.
  - **Drag-select copies within a pane; the right-click menu copies what a drag is bad at.** These were once alternatives — while the columns were cells of one row, a selection dragged down them would have handed back A and B interleaved, so the menu was the only copy on offer. With each pane its own document that argument is gone and an ordinary selection does the ordinary thing. The menu keeps the two jobs a selection is genuinely poor at: a whole side, which would otherwise be a drag through thousands of rows, and the comparison in unified `-`/`+` form, which is not text on screen at all and is the shape that survives being pasted into a ticket.
- Alternatives considered:
  - **A structural comparator per section — JSON-path diff, header key-set diff, query-params-as-a-set:** rejected. It reports differences more precisely than a text diff can (`data.items[3].price: 100 → 120`), but it is a different renderer per section, a novel UI to learn, and it was not what was asked for. Canonicalizing first recovers most of the same noise reduction with one familiar view.
  - **The diff engine in `host`, so `cli` and `mcp` could compare too:** rejected. `shared` may not depend on `host`, so this needs a third module under both trees — real structural cost for a capability an AI client already has by fetching two exchanges and diffing them itself.
  - **The docked right tool panel:** rejected. ADR-0021 gives it one slot at a fraction of the window width, and a two-column diff is the widest thing in the app.
  - **The detail panel below the list,** swapping `DetailPanel` for the diff while a comparison runs: built first, then replaced by the window above. It is the cheapest possible integration — no window lifecycle, no state to hoist, and the list stays visible — but it is bounded by the panel's height, which is the one dimension a diff cannot give up. Keeping it as an option alongside the window was also rejected: see the decision above.
  - **Following the selection rather than pinning the pair** (A is always the selected row): rejected once the diff became a window. It is the right rule for a panel that belongs to the selection and the wrong one for a window that does not — a click in the list would close a window the user had deliberately opened.
  - **A volatile-field ignore list** (`Date`, `X-Request-Id`, `traceparent`, `Set-Cookie`, and their JSON equivalents): deferred, not rejected. Sorting removes the ordering noise but not the per-call-unique *values*, which will still show up as changed lines. The section-text builders are the single place such a filter would go.
  - **A unified (single-column) view for a narrow window:** deferred. The window's 640dp floor keeps both columns usable, and a diff someone wants to read is one they will widen. The unified *text* now exists anyway, as the "Copy diff" action — if this is ever built, it renders from the same shape.
  - **Keeping red/green and relying on the `-`/`+` markers for colorblind readers:** superseded. The markers were the right answer to the question "how is add-versus-remove carried without hue" — but the better answer turned out to be that this view has no add-versus-remove to carry.
  - **A neutral (accent-derived) tint instead of a hue:** rejected. It is the only choice that could not collide with a syntax color at all, and the accent here is monochrome (ADR-0016), so the tint would be grey — which reads as dimmed or disabled, the opposite of what a line the reader is hunting for should look like.
  - **Collapsing unchanged regions instead of structural blocks** (the "expand 40 lines" of a web diff): deferred. It is the more powerful of the two for a long body with few changes, and it is not in tension with this — it folds by hunk where this folds by bracket, and the row-span machinery is the same. Structural folding went first because it is what the detail panel's editor already does, so it is the one that makes the two viewers behave alike.
  - **Dropping syntax color on every tinted row, rather than only inside the changed span:** rejected. It removes the collision completely, but it strips color from exactly the lines the user came to read, which is the wrong half to give up. Restricting the reset to the span keeps the rest of a changed line syntax-colored.
  - **Recoloring the JSON string token so it never matches the added tint:** rejected. The diff would then highlight JSON differently from the code editor two panels away, trading a contrast bug for an inconsistency — and it would only move the collision to whichever token got the green.
  - **Teaching the LCS itself to match similar (not just identical) lines,** which would fix the run-pairing problem at its source: rejected. It makes the table's recurrence depend on a fuzzy score, so the alignment stops being reproducible from the text and becomes sensitive to the threshold. Confining the fuzziness to the pairing step leaves the set of matched lines exactly as before and only decides how the *unmatched* ones are laid out beside each other.
  - **Never pairing lines that fail the correspondence test,** emitting them as separate one-sided rows instead: rejected. It is more honest in the abstract and strictly worse to read — a block of genuinely replaced lines would double in height and lose its inline highlights, which is the common case this view exists for.
  - **Emitting the canonical JSON without trailing commas at all,** so the two sides match literally: rejected. It fixes the alignment by making the displayed document invalid JSON, which the copy actions then hand out.
  - **Ignoring leading indentation as well as the trailing comma,** so that wrapping a payload in one new level of nesting does not report every line as changed: deferred. It is the same class of fix and the artifact is real, but it is materially riskier — a key that appears at two depths would start matching across them, and a bad alignment is worse than an honest block of changes. Worth revisiting with a depth-aware key rather than a blanket trim.
  - **Hiding the sort control on non-JSON sections instead of disabling it:** rejected. A control that vanishes as tabs change reads as a layout glitch, and it cannot explain itself; a disabled one can say *why*, which is the actual question ("can I sort an HTML body?").
  - **A second implementation of find for the diff,** or extracting the editor's viewer half into a shared component to get it: both rejected, and their being the only two options on the table was the signal that the renderer itself was wrong. Reusing `CodeEditor` outright makes find arrive with no diff-side code at all — Cmd+F opens the bar in whichever pane has focus and searches that side, which also answers "which side is the hit on" by construction rather than by reporting it.
  - **A `DiffEditor` component wrapping the two panes,** owning the shared state: rejected. It is one more layer between the panel and the editor whose entire content would be the four values the panel already computes, and it would need re-opening for every future diff-only affordance anyway.
  - **Rendering both sides into one editor as a unified `-`/`+` document:** rejected as the primary view. It reuses the editor even more completely — one document, no padding, no shared-state problem — but the ask was explicitly side-by-side, and a unified body halves the width available to each side's text.
- Consequences:
  - New `shared/format/TextDiff.kt`: `diffLines`, `inlineDiffRange`, `changeHunkStarts`. The alignment trims the identical head and tail before running Myers over the core — not only for speed, but because two captures of one endpoint differ in a handful of lines inside an identical envelope, so the trim is usually most of the work. Past `MAX_EDIT_DISTANCE` the core is reported as one wholesale replacement rather than a trace nobody could hold.
  - `changeHunkStarts` groups consecutive changed rows, so the next/previous buttons treat a ten-line change as one stop. The counter reads `3 / 12` while stepping, the bare total before the first step, and `identical` when there is nothing — a state an empty counter would leave someone hunting for.
  - `BodyFormatting.kt` gained `canonicalJson`, sitting beside the hand-rolled `parseJson`/`prettyPrintJson` it reuses — no JSON library, consistent with that file's existing stance. Numbers keep their source spelling, so precision survives; strings are re-escaped on the way out.
  - `TrafficList` took `compareIds`/`onToggleCompare` and an eighth context action. Both compared rows carry a 3dp accent bar, pinned outside the horizontally scrolling `Row` so it stays at the row's edge instead of sliding away with the columns. The bar and the selection's `surfaceVariant` fill are deliberately different marks: with the pair pinned, borrowing the fill would light three rows and say nothing about which two are being diffed. The bar does not distinguish A from B — the window's own header does, and 3dp has no room for a letter.
  - The pair lives in `Main.kt` as `comparePair: Pair<String, String>?`, not in `WailoViewer`, because only the host can own an OS window — the same reason `breakpointWindowOpen` lives there. `shared` gained `compareIds`/`onCompareChange` on `WailoApp` and `WailoViewer` to report a start or an end upward, and `WailoCompareWindowContent` as the window's root. `WailoViewer` is back to `DetailPanel` unconditionally, and its detail floor to a flat 180dp.
  - Both ids are resolved against the live entry list every composition, so clearing the capture closes the window rather than leaving it on rows that no longer exist. Swapping trades the two ids in place; the selection is untouched.
  - `WailoCompareWindowContent` re-provides `WailoTheme`, the text-scale `LocalDensity`, and — unlike the breakpoint window — `LocalBodyLoader`, since Compose shares no CompositionLocal across windows and a compare pane with no loader would render two empty documents rather than fail.
  - `WindowStateStore` gained a third instance (`compareWindow`), so the window reopens where it was left, and `Main.kt` a fourth raise counter: re-issuing the same pair is a no-op on the state, which would make the menu item look dead once the window is buried.
  - `IdentityStrip` takes the opposite side as well as its own, which is what lets it show a field only when the two disagree. Its detail line is built as an `AnnotatedString` and rendered only when non-empty, so two calls from one app carry no second line at all. Dropping the clock time took `zoneOffsetMillis` back out of `ComparePanel`, `WailoCompareWindowContent`, and `Main.kt`; the toolbar's close button went with it, since the window already has one in its title bar.
  - `pairUp` walks its two runs with a bounded lookahead (`PAIR_LOOKAHEAD`) instead of zipping them, and `correspond` judges a candidate pair. Both are bounded on purpose: the scan for shared text stops at `CORRESPOND_SCAN` characters from each end, and a long line is scored against that window rather than its true length, so two minified blobs agreeing for a few hundred characters still read as one line modified. Past `MAX_PAIR_SEARCH_LINES` no partner is searched for at all and the old positional zip stands — at that size the run is the wholesale-replacement fallback, where the pairing is guesswork anyway.
  - `diffLines` gained a `key` parameter defaulting to identity, and `jsonLineKey` beside it. The keys are computed once per line rather than inside the LCS recurrence, which reads every pair. `ComparePanel` passes `jsonLineKey` exactly when its JSON sniff says so, so headers and the summary — where a trailing comma would be content — are unaffected. A side effect worth knowing: the fix makes the change counter more honest as well as the tint, because the spurious middle row was welding otherwise separate hunks into one stop.
  - `urlAnnotated` went from private to internal in `DetailPanel.kt`, so both headers color a URL the same way; the compare strips wrap theirs in `SelectionContainer`, which the detail panel's own header already does.
  - `CodeEditor` gained one optional parameter, `decor: CodeEditorDecor?`, null for every ordinary use — so the plain editor's behaviour is unchanged by construction. It carries this pane's `LazyListState`, the shared `ScrollState` and wrap flag, the per-row gutter number (null on a filler, whose gutter stays blank), the opposite side's line length and longest line, the row tint and inline span, the fold pair (`foldSpans` merged, `foldArrows` per side), and which pane draws the vertical scrollbar. `Fold` and `computeFoldRegions` went from private to internal to be reachable.
  - Two changes inside the editor needed care because they touch the single-editor path. Its caret-follow effect now returns early for an *unfocused* diff pane: with one shared scroll position, the idle pane's caret sits at line 0 and would drag the pair back to the top whenever a fold re-ran the effect. And the content width takes the max of both sides' longest line, since one `ScrollState` has one travel — sized to one pane, the wider side could not be scrolled to its end.
  - `DiffPanes` shrank from a two-cell-row renderer plus `DiffCell`, `DiffPalette`, and `diffAnnotated` to two `CodeEditor` calls and the values they share. The panel's own `MAX_HIGHLIGHT_LINE` and `MAX_CONTENT_WIDTH_PX` went with them — the editor carries both — and `foldableRowSpans` was deleted from `TextDiff.kt` along with its three tests, which is the point: the bracket scan now exists once.
  - The tints survive as three values rather than a palette class: 0.16/0.12 for a changed row, 0.38/0.30 for the inline span (dark/light), and 0.04 for a filler band. The span still overrides the token color in its range only, now inside `EditorLineRow`'s own annotation pass.
  - `ComparePanel` builds two `CodeEditorState`s from `rows`, each side padded with blank lines, and holds the collapsed openers in a `mutableStateListOf` keyed on the rows so a new diff starts unfolded. `mergeFoldSpans` unions the two per-side maps to the later close; `hiddenUnder` derives the hidden set for `stepHunk`, while each pane derives its own from the same spans.
