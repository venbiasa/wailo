# ADR-0064 — One global tools gate above the per-feature masters, owned by the daemon

- Status: Superseded by ADR-0066, and never shipped. Its reading of the force was wrong: "stop intercepting from a menu with no panels in it" was taken as a demand for one new switch, when the menu can simply carry the switches that already exist. ADR-0030's rejection of a global master therefore stands unamended. What survived is the *shape* the gate was designed with — daemon-owned so it holds with no window open, non-destructive so re-arming restores what was armed — which is what each per-feature master already was.
- Context: ADR-0030 gave each interception feature its own master switch and explicitly rejected a single global one, because the ask then was per-feature and the tool rail already put each switch beside its own controls. The menu bar item (ADR-0063) changes the force: it has to offer "stop intercepting" from a menu with no panels in it, and the daemon it represents can be serving an MCP client with no Studio window at all. Meanwhile ADR-0061 moved this configuration onto the daemon, so a frontend-local flag would no longer be in the right place even if the menu did not exist.
- Decision:
  - **The global gate is additive, not a replacement.** ADR-0030's rejection stands as written — the per-feature masters remain, and each panel keeps its own switch. This is one gate *above* them: shut, no feature acts; open, every feature resumes whatever its own master says. It never writes a feature's master, so the two are independent and the combination the user arranged survives a round trip.
  - **Same non-destructive rule as ADR-0030, one level up.** Off withholds Map Local rules, breakpoint rules, and the capture filter from the push, and declines to spend Seeds. Nothing stored changes, so re-arming resumes exactly what was armed, and there is still no wire concept for it: an empty rule set and both-lists-off are pushes the device already understands (ADR-0019/0029).
  - **It lives on the daemon, like the MCP gate (ADR-0059).** It has to keep holding with no Studio open, must not re-arm because the frontend that shut it was closed, and must read the same to Studio, the CLI, and MCP. It persists in daemon settings and defaults **on**, so an older settings file upgrades into an open gate rather than into tools that appear silently broken.
  - **Poll reports the authored state, never the gated push.** `HeadlessHost` keeps the requested capture filter separately from the one the engine is running, and the daemon reports the requested one. Without that split, a frontend polls back the disarmed filter, cannot tell it apart from the user having cleared it, and persists it — so the gate would erase the arming it exists to preserve. The same reasoning keeps `mapLocalRules` and the breakpoint masters reporting what was authored.
  - **The gate pauses Seed spend; the Seed master still clears the queue.** A fill the Seed feature's own switch declines drops the queue, which is right for an explicit "I do not want these". The global gate is a pause over everything at once, so it keeps the queue it declines to spend, and reopening sweeps the holds that arrived while it was shut — nothing else would come along to answer them.
  - **A shut gate makes each per-feature master read *disabled*, not off.** The panels take it as a separate input from the master's own value, rather than folding the two into one effective boolean: a switch that shows off and then refuses to move when clicked looks broken, and the user cannot tell a gated feature from one they turned off themselves. It is also a Settings row, not only a menu item, so it is discoverable with the menu closed and explains itself in place.
- Alternatives considered:
  - **Have the menu flip all four per-feature masters:** rejected — destructive in the one way ADR-0030 refused. It cannot restore the previous combination, and re-enabling would arm a feature the user had deliberately switched off.
  - **A Studio-local flag:** rejected — it would not hold for an MCP session with no window open, and it would re-arm every tool the moment the frontend that shut it closed.
  - **Gate in `engine`:** rejected — the engine is a relay (invariant #2), and the daemon is where the state that outlives frontends belongs.
  - **Report the gated filter on poll and teach frontends not to persist it:** rejected — it makes every current and future frontend responsible for knowing which pushes are real, and one that forgets corrupts the user's saved filter silently.
  - **Fold the gate into the value each panel's master reads:** rejected — see above; it hides why the switch will not move.
- Consequences:
  - Turning tools off *increases* captured traffic, because the capture filter is one of the things it disarms and both-lists-off means "capture everything". It is a gate over interception, not over recording — Record Traffic is the separate control for that.
  - MCP and the CLI read the authored configuration whether the gate is open or shut, so an agent listing rules sees what is configured; `status` reports the gate, which is how it can explain a rule that is not firing rather than concluding the rule is wrong.
  - The control protocol version is bumped, so a frontend that expects the gate replaces an older daemon that cannot report it (ADR-0058).
  - There are now four levels of "disabled but remembered" — global gate ⊃ feature master ⊃ group ⊃ rule — all rendered the same way. That is one more than ADR-0030 planned for, and the top one is the only one the panel cannot change.
  - Manual smoke: arm Map Local, a breakpoint, and an allowlist, then shut the gate from the menu bar item and confirm the device falls through to the network, nothing pauses, all traffic is captured, and each panel dims with its master disabled but still showing what was armed. Reopen it and confirm the exact prior arming resumes, including a feature whose own master was off staying off. Check both themes on the dimmed panels (ADR-0016).
